### Added

- `ask-decision`: the fifth part of a decision item is now **Act** — the runnable act (a fenced `sh`
  block that runs top to bottom, or a fenced `url` block for a browser step) followed by the
  post-act check. Its comments are plain text on their own lines — letters, digits, spaces, tabs
  and `. , : - / _ + #`, no trailing comments — and stand only in the header straight after the
  guard; each step inside the act function opens with `echo '<n>. <text>'` instead. Interactive
  zsh does not treat `#` as a comment by default: it runs a `;`, backtick span or `$(...)` in a
  comment line, and even a plain one is a command that fails, which changes the branch taken
  after `&&` or `||`, in a condition or last in a tested group, while after a line continuation
  its text runs in every shell. These two rules together are the only control on a block's first
  paste. The block opens with a zsh comment guard
  (`[ -n "${ZSH_VERSION-}" ] && setopt interactive_comments`), which covers only what zsh reads
  after it: a bracketed paste is read whole before its first line runs, so the guard never protects
  the paste that carries it. Values only the human has are marked `# fill:`, and every secret is
  read, after the driver-token pin and before any live step, as `NAME=; read -rs NAME || { ...; exit 1; }`, so a shell whose `read`
  has no `-s` stops instead of passing an inherited value, and an empty read stops before any
  change. The block defines the act as one function with a per-act name (`driver_act_<id>`) run in
  a subshell: pasting it only prints, the driver acts by calling it with `live`, a live run never
  carries over to the next act's paste, and a block that fails to parse leaves no earlier act under
  the name the driver types. Only the desk-authored block is the act — one posted by any desk role's
  own App identity, on any surface, and not edited since by any other account; a block copied from a
  comment or an untrusted issue is never run, and an agent never runs an Act block. `worker-desk`,
  `verify-desk` and `the-desk` point at that one definition for the `BLOCKED-ON-HUMAN` report and
  the verify-gate card. The Reply shape (part 4) keeps its ruling command and the driver-token,
  fail-closed rule for ruling and act alike, and points an act at this Act block; an act is not a
  one-line command. The Act block pins the driver's token itself: the act function's first step is
  `GH_TOKEN="$(gh auth token --user "<driver-login>")" || exit 1` then `export GH_TOKEN; unset
  GITHUB_TOKEN`, scoped to the function's subshell, so an exported role-App token or the active
  account never decides who runs a `gh` step. The
  renderers (`assay-inbox.sh`, `deskinbox walk`) print the Reply shape's `command:` line and
  still label the fifth part `Verification`.
- `skillslint`: a hard `ACT-BLOCK` check holds every act block the plugin ships under `plugins/` (an
  `sh`, `bash`, `zsh` or `shell` fence) to the comment rule (plain text, header only, no trailing comment), the
  zsh guard as its first line, a per-act function name and the safe secret read (exit 1 on a
  violation, exit 2 when it finds no act block at all). A trailing comment is any `#` straight
  after a blank or after a character that ends a bash or zsh operator (`;`, `&`, `|`, `(`, `)`, `<`,
  `>`, a backtick, `!`, `-`), flagged per line whatever the quotes around it, so `"a;#b"` fails too.
  A best-effort scanner also reads the block whole, with its quotes, `$'...'`, spans, arithmetic and
  heredocs. It adds a `#` that starts a word on a continuation line. It fails where the block ends
  inside one of them, and on a listed set of constructs it could misread: a heredoc whose span closes
  on its line or opens after it, a `<<` in arithmetic, a `$` or backtick in a heredoc delimiter,
  and a `${` followed by a blank or `|`. The read rule is a syntactic shape check, best effort: it
  accepts only the whole one-line shape — the clear first, `read -rs` with no other option, and a
  failure branch ending in an `exit` from 1 to 255 — and flags a read it sees inside a `( )`
  subshell, `$( )`, backticks, a `|` pipeline, a background `&` or another function, plus any other
  word that is `read` once quotes and backslashes are removed. It does not prove the read runs in
  the act function's own shell: it does not model `|&` piping, a backslash line continuation
  before a `|` or `&`, a redirect whose target is a command substitution, a heredoc body fed to a
  shell, a `#` straight after an operator, an operator inside `${X:-…}`, `$'…'` quoting, a
  function that shadows `exit`, or a read run through `eval`, `sh -c` or an expanded command name,
  and a read in one of those can pass. A sixth rule holds the driver-token pin: in a block with a
  `gh` step, the act function pins the driver's token at its top level before the first `gh` step
  (the `GH_TOKEN=` assignment ending `|| exit`, standing as its own statement, then a separate
  `export GH_TOKEN` and an `unset` of `GITHUB_TOKEN`). The login is one quoted literal word (unquoted, the placeholder is a
  redirect and a block that fails to parse runs its live steps on a bash paste); the pin governs `gh`
  only, not a `git push`'s credential helper, `GH_HOST` or the enterprise-token variables. It fails the
  block on a `{ }` function body, a login given as an expansion, a `gh` step ahead of the pin or
  outside the function; a pin inside an `if`, loop, group or subshell, after `||`, `&&`,
  `|` or `|&`, under `!`, `time` or `env`, or followed by a pipe; after the pin, a set of either
  variable (a bare assignment, or one given to `export`, `declare`, `typeset`, `local` or
  `readonly`), an `unset GH_TOKEN`, `export -n GH_TOKEN` and `declare +x GH_TOKEN` (the builtin's
  name may be quoted or escaped); a `gh` step run through `env -u GH_TOKEN`, `sudo` or `doas`; and any
  `env` word before a `gh` step that is not `NAME=value`, `-u NAME`, `--unset=NAME` or `--` (that
  allowlist is the whole model of `env`: `env -i`, a cluster, any other option refuses). It is syntactic and best effort.
  The lint refuses the shapes it models; the pin inside the function is the control. Not
  modelled (examples, not exhaustive; a `gh` step in one can run with no pin, and a token change
  in one can undo the pin): a `gh` run through `eval`, `sh -c`, `bash -c`, `xargs`, `nice`,
  `timeout`, `stdbuf`, `exec -c` or a wrapper command the lint does not name, or one whose name
  is quoted, escaped or given by path (`\env`, `"sudo"`, `\builtin`, `/usr/bin/env -i gh`); a
  wrapper option that takes a separate argument and is not in the lint's list (`time --output FILE`, say);
  an alias; a command name built from an expansion; a function that wraps `gh`, or one that
  shadows `export` or `unset`; a pin inside a heredoc body; a `trap … DEBUG`; a `gh` step inside
  a process substitution (`<( )`, `>( )`), after a leading redirect such as `2>&1`, or in a
  `case` arm whose pattern opens with `(`; a `case` pattern `)` that no `esac` closes; an
  `export` or `unset` of the token run under `||`, `&&`, `&` or a pipe; a change of either token
  variable by `read`, `printf -v`, `for`, `select`, `let`, `mapfile`, `getopts`, `source`, `.`,
  a nameref, `eval`, zsh `integer` or `float`, or zsh `${GH_TOKEN::=…}`; a token change by an
  `export` option cluster holding `n` (`-pn`), by a bare `local`, `declare` or `typeset` of the
  token with no value (zsh), or by zsh `unset -m`. The pin governs `gh` only: a `git push` uses
  git's credential helper, and `GH_HOST` and the enterprise-token variables are left alone,
  which matters only against a GitHub Enterprise Server host. Act blocks a
  desk writes at run time are not linted.
- `deskfile new` refuses (exit 5) a human-only hand-off — label `human-only`, or a body whose first
  non-blank line opens with `BLOCKED-ON-HUMAN` — whose body carries neither a ` ```sh ` nor a
  ` ```url ` fence. Fences are matched the CommonMark way: a run of three or more backticks or
  tildes, indented at most three columns from its margin or list item, so an `sh` fence quoted
  inside another block, or indented four columns into code, does not count. The gate checks that a fence exists, not what is in it.
  `--force-new --reason` is the only bypass, and it also waives the dedupe search, the
  blocker-evidence gate and, on a `needs-decision` filing, the fork-test gate; the audit line
  records `act-gate=bypassed:force-new`.
- `deskfile new`: a body led by `BLOCKED-ON-HUMAN` is a human-only hand-off for the fork-test gate
  too, just like the `human-only` label, so it can no longer take the notice lane and drop
  `needs-decision`, and `--no-fork` refuses it (exit 5).
