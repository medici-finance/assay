### Fixed
- The body/diff scanner's decrypted-Kubernetes-Secret rule no longer refuses a ConfigMap's plaintext `data:` just because a correctly sops-encrypted Secret sits elsewhere in the same text. A `data:`/`stringData:` mapping is now skipped only when a YAML parse proves that its owning object has exactly one `kind`, that the kind is not Secret, and that no Secret encloses it. The proof has to hold in every way the text can be read: as a diff (only whole new-file hunks are parsed), as a whole YAML stream, and as markdown fences. Every line that declares a Secret has to be accounted for by that same parse. Anything the parse cannot prove keeps the earlier refusal. That includes text that does not parse, mappings in modification hunks, duplicate or merged kinds, and readings that disagree. One consequence: editing an existing Secret beside a new ConfigMap still refuses.
