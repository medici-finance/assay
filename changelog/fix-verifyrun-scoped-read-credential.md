### Fixed
- An admitted `statusgen --verifyrun` that reads an acceptance approval (`--acceptance-forge`) now reads it only with a read-only verifier credential that the run mints for itself. The credential is narrowed to the attested repository, minted on first use, never cached, and revoked and deleted when the run ends. The run ignores `GH_TOKEN`, `GITHUB_TOKEN` and the forge CLI's stored login, and so does every other forge read inside an admitted run or an admitted Verify row, REST or CLI. The credential is missing if no `desktoken` is on `PATH`, the role is refused, the grant is wider than read, the mint fails or the file fails its checks, and each of these makes the read could-not-check, never a pass. Only a Verify row whose command passes `--acceptance-forge` is handed the credential, as a file path in `ASSAY_VERIFYRUN_READ_CREDENTIAL`; the value itself is never in a row's environment or output. Unadmitted runs are unchanged.

### Added
- `desktoken <role> --repo <owner/name> --read-only-out <path>` (GitHub): mints a credential narrowed to that one repository with issues, metadata and pull-request read only, into a new 0600 file inside an existing private directory, with its granted map beside it in `<path>.perms`. It is never cached, and it cannot be combined with `--ttl`, `--fresh` or GitLab. A grant the forge returns wider than read is revoked at once and refused with nothing written (exit 6).
