### Fixed
- The release workflow tests again check that every mutation harness and every `deskmerge` shard in the release test matrix runs exactly once, uploads its report and keeps its verdict gate. The test matrix must hold exactly its eight legs, including the suites that are not mutation harnesses. A harness step, the report upload or the test job that tolerates failure, a surviving mutation that exits successfully, a shell override (including a workflow-level `defaults` placed after the jobs), an excluded leg, a disabled or non-failing report upload, a publishing job that stops waiting on the test job, and any job-level `if` on a publishing job are each refused. Settings are read by a strict reader of plain block-style YAML (`tools/release/workflow_keys.py`): a trailing comment is ignored, a setting kept only in a comment counts as absent, keys are read without case, and a line at top level or in a checked job written in any other form (a quoted key, a space before the colon, a flow mapping, an anchor or merge key, a repeated key, a plain, quoted or flow value spread over several lines) is refused rather than skipped. A block scalar is accepted only as a step's `run` value or a value under a step's `with`, so a skipped body never hides settings, and each job's and step's text is cut where that reader ends it; a step name used twice in one job counts as no step at all. The `artifacts`, `runner-arm64` and `release` jobs and their steps refuse `continue-on-error` in any form (the two optional release Go cache steps excepted), the workflow environment must hold only `GO_VERSION`, and the test job must not set its own. They also check that the `artifacts` and `release` jobs bind their fixed runner labels with no expression, that the publisher's runner label matches exactly (a label that merely contains it, or appears only in a comment, is refused), and that the native arm64 job downloads every build artifact and fails on an empty upload. A new `tools/release/ci_step_test.py` checks from outside the image contract suite that CI still runs it on the `rest` shard, fails the shard when it fails (no shell override, no excluded shard) and stops it within 15 minutes, and that the Go regression test that also runs every release suite is unchanged; the CI step check reads `ci.yml` through the same strict reader, refuses a job-level `if` or `env` on the shard job, holds the step to its `name`, `if`, `timeout-minutes` and `run` keys, and pins the Go regression test file whole, so the test cannot be commented out or moved into a string.
