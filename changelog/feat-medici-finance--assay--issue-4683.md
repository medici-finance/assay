### Fixed
- Container-netns Verify rows now resolve Go modules from the source under verification, not from the module cache baked into the runner image when it was built (#4683). When the verified home lists Go module roots in `images/verify-runner/go-module-roots.txt`, `statusgen verifyrun --open-bracket` requires `--module-cache <dir>`, a new empty directory outside the home and outside the host's own module cache. On the host it runs `go mod download` for each root against its committed `go.sum` with checksum verification on, records the cache digest in the receipt, and prints the container flags that mount the cache read-only. A failed download is could-not-check with no receipt; the baked cache is never a fall-back.
- The container run refuses before any row unless that cache is mounted read-only on a read-only root, matches the receipt's digest, and runs under `GOPROXY=off` and `GOTOOLCHAIN=local` with no checksum-loosening setting. The witness records the digest as a `Module-Cache:` line inside the bracket's digested span, and `--close-bracket` refuses a witness whose `Module-Cache` is not the receipt's.
- Before its first download the open step screens every module path a root could request against the same approved public set as the cluster stager. A path under the verified repository's owner, one matching the operator's private patterns, or one off the set is could-not-check with nothing sent to the proxy. It then prints the proxy, checksum database and roots it will contact. The download environment is built from nothing (scratch `HOME`, `PATH` and the pins), and the cache path may hold no comma, quote or whitespace.
- On a home that lists module roots, the container run and `--close-bracket` refuse a receipt with no `module_cache`, or one recorded for other roots.
- The runner image reads its module roots from the same tracked `go-module-roots.txt` instead of a list written into the Dockerfile.
