### Fixed
- statusgen's held scan now treats an Evidence row keyed `3 (Verify 3, negative)` as the same Verify row as a later run's bare `3`, so a later strict `VERIFY: PASS` that re-ran row 3 clean under the bare key supersedes the older annotated row. Only the earlier entries are shortened; a later row keyed with an annotation covers nothing. Before this, the annotation made the keys differ and `verifyflip` kept reading the old row as live. The key is shortened only when every number in the annotation is the row's own number. It is never shortened for a lettered key (`3a`), nested parentheses, text after the annotation, or a number that names another row or a date. It is also left as written when the same number shows up with two different annotations anywhere in the Evidence, or in two forms within one entry, because those may be sub-rows.
- The held scan no longer reads `could-not-check` as a row's disposition when the row's Result cell is recording what the product printed, such as `PASS: … a could-not-check mission section`. The cell must match a closed grammar: the table has an Exit column and every Exit cell of the row is clean; the Result cell opens on PASS, passed or ok; an article or possessive comes right before the marker, with a verb of output (prints, yields, lists) in the same clause; the marker is followed by a known noun (mission section, banner, heading, label) and then only neutral words; the line has no struck text; and the row has no hold word. Any other wording is read as a hold. `HELD` is never excused this way.
- A summary such as `Rows: 2 of 2 required rows passed; 0 could-not-check.` is now read as a zero count instead of a held disposition. This applies only when both counts are the same and above zero.
