### Added
- Coverage can judge a witness's recorded read set, behind one switch that stays off in this release (see the next item): a `(reads sha256:<hex>)` token in the Runner cell names a `reads/<hex>` file next to the brief, honoured only when it arrived in the same commit as its row, and a change to a path outside that set no longer holds the claim. Any recorded go build must also cover a compile-input floor that statusgen computes with `go list -deps -test` over the witness tree, so a recorder that misses a compiled file still fails closed. The floor is computed only for a read set that is already admitted, from a contained export of the tree, in an environment statusgen builds (no settings file, network or toolchain switch) with a time limit; a recorded flag or setting it does not reproduce, an empty floor and a package outside the tree are could-not-check. A read set evaluated with no floor is could-not-check.
- `verifyrun` writes a read-set token on every executed row. This release ships no recorder, so the token it writes is always `(reads could-not-check: …)` and no read-set file is written. Off Linux the reason is `recorder is Linux-only (<os>)`. The judge agrees: until a recorder ships, the switch `readSetRecorderShipped` in `statusgen/readset_platform.go` is false, so autoflip, the reconcile fold and `--coverage` observe no read set and treat any `(reads sha256:…)` token, whoever landed it, as could-not-check with the reason `no read-set recorder in this build`. A row carrying one is judged exactly as the same row without it, and its reason names the missing recorder.

### Changed
- `deskevidence` refuses, before any forge call, to land a row that names a read-set file, because its one-file write cannot commit the row and the file together. A row whose file is absent or carries another digest gets a refusal that says so.
- A brief's own new read-set files named by its Evidence no longer mark `verifyrun`'s tree `+dirty`. Read-set files of other briefs still do.
