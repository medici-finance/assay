# Registers v1.0-draft — Specification

**Version:** v1.0-draft
**Status:** DRAFT — published for review. v1.0-draft is unstable: breaking changes MAY be
made without a major-version bump; no stability commitment.
**Describes reference implementation:** `statusgen/v0.8.0`

## 1. Scope

This document specifies the append-only registers — FINDINGS, INTAKE and REQUIREMENTS —
that form the system's memory: what invalidated a plan (FINDINGS), what raw ideas are
queued (INTAKE), and what the product was asked to do (REQUIREMENTS). A conforming
implementation MUST maintain each register as an append-only log that satisfies every
MUST in this document.

Section 7 (RETRO) is **informative, not normative** — see the note there.

### 1.1 Terminology

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD",
"SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be
interpreted as described in RFC 2119.

## 2. File locations

### 2.1 Source of record: per-entry files

Each register entry MUST be a **separate file** under its register's entry directory:

- FINDINGS entries: `docs/streams/findings/<slug>.md`
- INTAKE entries: `docs/streams/intake/<slug>.md`
- REQUIREMENTS entries: `docs/streams/requirements/<slug>.md`

One entry per file. This is the source of record — the only thing an author writes.
Per-entry files exist so that parallel authors never contend for the same lines of the
same file; that property is the reason for most of the rules below.

### 2.2 Generated views

`docs/streams/FINDINGS.md`, `docs/streams/INTAKE.md` and `docs/streams/REQUIREMENTS.md`
are **generated views** of the entry directories, not source. A conforming implementation:

- MUST regenerate each view from the entry files.
- MUST treat the views as single-writer — written only by the trunk branch's CI, never
  committed from a feature branch, in the same discipline as the status board.
- MUST NOT require, and SHOULD actively discourage, hand-editing a view. The reference
  implementation emits a NOTICE when a document links a generated view instead of the
  per-entry file behind it.

An implementation MAY additionally accept a legacy single-file register (all entries as
headings inside `FINDINGS.md` / `INTAKE.md`) as a **migration compatibility shim**. That
form is not conforming for new registers, and an implementation that accepts it MUST
still treat the per-entry directory as authoritative wherever both are present.

An implementation that scaffolds a new tracking root MUST scaffold the conforming form:
the entry directories of section 2.1, with slug-form IDs. Scaffolding the compatibility
shim hands every new adopter a non-conforming register on their first command. The
reference implementation currently does exactly that — see `spec/README.md`
§ "Known divergences from the reference implementation".

## 3. Shared conventions

### 3.1 Append-only

A new entry MUST be added as a new file. Existing entry files MUST NOT be edited away
or deleted. Registers are the audit trail; a silent edit erases the record of why a
decision was made.

Amending an existing entry is permitted only for the transitions section 3.3 names
(flipping a disposition or resolution, and explaining why). A conforming implementation
SHOULD detect in-place gutting of an entry's load-bearing fields by comparing against
the version of the entry that has already landed on the trunk branch.

### 3.2 Deletion detection (no contiguity check)

Entry IDs are slugs (section 3.4), not a counter, so they carry **no contiguity
guarantee** — there is no sequence to have a gap in, and an implementation MUST NOT
claim gap-detection as a property of this scheme. Slugs trade contiguity away
deliberately, to buy collision-free parallel writes.

Deletion is instead made visible by three properties, which a conforming implementation
MUST provide together:

1. **Tombstone check against history.** Any entry file that has ever existed on the
   trunk branch but is absent from the working tree MUST be flagged. This is what
   catches a deletion; it replaces the contiguity check, and it is strictly stronger
   for the case it covers, because it names the missing file rather than inferring a
   gap.
2. **Duplicate-ID check.** Two entries sharing an `id` MUST be flagged.
3. **Diff visibility.** Because an entry is a whole file and the view is regenerated by
   a single writer on trunk, both a deleted entry file and its disappearance from the
   view are visible in a change-set diff.

**Limit — the tombstone check is advisory, not a guarantee.** It is a history
comparison, so it can only run where that history is available: in the reference
implementation it returns nothing when run outside a repository checkout, and skips on
any history-read error. A run in which the check could not execute is presently
indistinguishable from a run in which it executed and found nothing. Treat a clean
result as "no deletion observed", never as "no deletion occurred". See
`spec/README.md` § "Known divergences from the reference implementation".

### 3.3 Withdrawal is a tombstone

To retract an entry, its file MUST be preserved. The entry's disposition or resolution
MUST be flipped, and the body MUST explain the withdrawal. Deleting the file both loses
the record and trips the tombstone check in section 3.2.

### 3.4 Typed IDs

Entries MUST reference briefs and other entries by typed ID (`<stream>/<NN>`,
`F-<slug>`, `I-<slug>`, `REQ-<slug>`). Prose names MUST NOT be used as identifiers.

Register entry IDs MUST use the slug form:

- FINDINGS: `F-<slug>`
- INTAKE: `I-<slug>`
- REQUIREMENTS: `REQ-<slug>` (`R-<slug>` is reserved by the RETRO register of
  section 7 and MUST NOT be used for a requirement)

where `<slug>` is 10–20 characters of `[a-z0-9-]`, starting and ending with `[a-z0-9]`,
derived from the entry's title. Example: `F-ws-token-expiry`.

A conforming linter MUST reject the numeric counter form (`F-01`, `I-07`) on a **new**
entry — a counter reintroduces the write contention slugs exist to remove. Numeric IDs
on entries that have already landed on the trunk branch are grandfathered legacy and
MUST remain valid.

### 3.5 Severity axis at design time

Any NEW register schema MUST define an impact/severity axis as a first-class field at
design time. A register without a severity axis cannot rank its own backlog: every entry
reads as equally urgent, and the axis can only be retrofitted afterwards with a
default-everything backfill that carries no real signal.

- A conforming NEW register schema MUST carry a severity/impact field on every entry.
- The field MUST be present from the schema's first version; it MUST NOT be introduced by
  a later backfill that assigns a single default to the existing corpus, because such a
  backfill records a value nobody judged.
- A register MAY choose the axis's vocabulary (an ordered set of levels, a numeric scale),
  but it MUST be an ordered axis a validator can sort on, not a free-text note.

This requirement is prospective: it binds registers designed after this section lands.
The FINDINGS register (section 4) predates it and launched without a severity axis — the
specimen that motivated the rule — and is not retrofitted here; adding an axis to an
existing register is that register's own scoped change.

## 4. FINDINGS register

### 4.1 Purpose

A FINDING is new knowledge that makes an existing brief wrong or stale. A conforming
validator MUST flag every affected brief and exclude it from the Next-up queue until
the finding resolves.

### 4.2 Format

Each entry is a file under `docs/streams/findings/` with YAML frontmatter and a prose
body:

```
---
id: F-<slug>
date: "YYYY-MM-DD"
title: "<title>"
affects: ["<stream>/<NN>", ...]
ack: ""                  # OPTIONAL — dated, attributed desk judgment that the finding is real
resolved: false
---

<body: what was found, the evidence, the fix direction>
```

### 4.3 Rules

- `id` MUST be a slug-form ID per section 3.4.
- `affects` MUST list one or more typed brief IDs.
- Resolution: update the affected brief or README to reflect the finding, then set
  `resolved: true`. A conforming validator MUST remove the brief from the stale-flagged
  exclusion list when `resolved` is true.
- An unresolved finding MUST keep the affected brief flagged and excluded from Next-up.

### 4.4 The Ack line (denial-of-service mitigation)

Filing a finding is unverified input — any identity can write a paragraph. The `ack:`
field is an OPTIONAL, dated, attributed judgment from an authorized desk that the
finding is real. Its semantics:

- Without an `ack:`, an unresolved finding MUST NOT hard-error an in-flight brief; it
  MUST flag and exclude from Next-up with a non-fatal notice.
- With a desk `ack:` against an `in-progress` or `implemented` brief, it MUST become a
  hard error, telling the operator to demote the brief (re-gate) or resolve the finding.
- A malformed `ack:` (missing date, missing attribution, or unparseable) **on an
  unresolved finding** MUST be a hard error. A conforming linter MUST flag it.
  A resolved finding is fully inert: a malformed `ack:` in a resolved entry MUST NOT
  hard-error, because nobody should be forced to rewrite register history to make the
  checker pass.

### 4.5 Finding→control closure (`class:` / `control:`)

A finding records that something went wrong. Recording it is not the same as
adapting so the *class* of wrong cannot recur. Two OPTIONAL frontmatter fields make
that adaptation trackable — an adaptation of procoder's blocking lessons-loop,
where an escaped bug's class must land a permanent control (a lint rule, a pinned
test, a rubric line) before the work counts complete.

```
class: recurring | one-off      # OPTIONAL; absent reads as one-off
control: <stream>/<NN> | <check-name> | <pinned-test-path>   # OPTIONAL
```

- **`class:`** — `recurring` marks a finding as naming a bug *class* the house
  expects to recur, so closing the one instance is not closing the class. `one-off`
  (or an absent field — the default) marks an instance with no expected recurrence.
  Only a `recurring` finding is expected to name a control.
- **`control:`** — a typed reference to the LANDED adaptation that closes the
  class. Three forms are valid: a brief ID (`<stream>/<NN>`), a lint/check name, or
  a pinned-test path. Absent = no control named.

**Closure means a landed artifact, not a promise** (procoder's meaning, adapted).
The control must be something that has actually landed. A `control:` naming a
`todo`/`in-progress` brief is legal — the brief is the *tracked closure vehicle* —
but it does not yet count as closed: the check keeps listing the finding until that
brief is `done`, which it reads from the same board data. A `control:` naming a
lint/check name or a pinned-test path is trusted as already landed (the check does
not audit the named artifact's existence — this instrument targets the *missing*
control, not the named ones).

**The check is advisory-first, and that is a deliberate difference from procoder.**
procoder *blocks* completion until the class is closed. The house lands this as an
advisory NOTICE this phase — `finding-without-control`, listed with the finding's
age — not a hard PROBLEM. The reason is honesty about the backlog: a hard gate over
an unclassified legacy register would only manufacture false-positives, because
every legacy finding predates the `class:` field. The backlog must be *classifiable
first* (findings opting in via `class: recurring`) before the debt can honestly be
forced. Escalation to a hard error is a later, separate decision — it is not
implied by adding these fields. This mirrors the same escalation posture the
worklist gate-why NOTICE takes.

The NOTICE fires only when a finding is unresolved AND `class: recurring` AND
either names no `control:` or names a control that has not landed. A resolved
finding is closed and inert (like a tombstone), so it is never flagged.

## 5. INTAKE register

### 5.1 Purpose

INTAKE entries are the raw-idea front door: brainstorms, "we should..." notions,
strategy fragments — while they are neither rejected nor scoped into work. INTAKE
entries are NOT briefs: they carry no waves and no DoD.

### 5.2 Format

Each entry is a file under `docs/streams/intake/`, rendering into the generated view as:

```
## I-<slug> — YYYY-MM-DD — title
<one paragraph>
Disposition: new | watching | scoped → <stream> | rejected — <why> | decision-needed → issue #NN
```

### 5.3 Rules

- `id` MUST be a slug-form ID per section 3.4.
- An idea becomes work ONLY by becoming a stream (scoping doc + brief authoring) or a
  brief in an existing stream; at that point, its disposition MUST change to
  `scoped → <stream>`.
- The disposition field is the single place that states whether an idea is live,
  parked, or dead. A conforming linter MUST NOT infer disposition from surrounding prose.
- Only `new` counts as untriaged for age alarms. Any other value reads as triaged, so an
  entry whose question has already been answered MUST NOT be left `new` — it would
  report intake debt that does not exist.
- Withdrawal: keep the file, set `Disposition: rejected — <why>`, and explain in the
  body. The file MUST NOT be deleted.

## 6. REQUIREMENTS register

### 6.1 Purpose

A REQUIREMENT is a recorded ask: what someone wanted the product to do, in that
person's terms, with the criteria that would settle whether the ask was met. It is the
first link of the chain ask → work → evidence → release. Without it, acceptance criteria
exist only inside an individual brief's Verify table, where they cannot be ranked, rolled
up, or shown to a reader who wants to know what a release was *for*.

A REQUIREMENT is NOT a brief: it carries no wave, no dependency edges, no DoD, and no
implementation plan. It states the ask and the bar; a brief states the work.

### 6.2 Format

Each entry is a file under `docs/streams/requirements/` with YAML frontmatter and a
prose body:

```
---
id: REQ-<slug>
date: "YYYY-MM-DD"
title: "<one line, in the asker's terms>"
impact: minor | major | critical    # the ordered axis required by section 3.5
asked-by: "<the seat that wants it>"
acceptance:
  - "<a criterion a Verify row could be written against>"
status: proposed | accepted | satisfied | withdrawn
satisfied-by: ["<stream>/<NN>", ...]   # OPTIONAL — typed brief IDs
---

<body: the ask, the constraint behind it, and what is explicitly not being asked for>
```

**`impact` is the section 3.5 ordered axis**, lowest to highest: `minor` < `major` <
`critical`. The levels are defined by consequence-if-unmet, so that two people ranking
the same ask land on the same level:

| Level | Meaning |
|-------|---------|
| `critical` | A central claim of the product is false, or a named user cannot proceed at all, until this is met. |
| `major` | A named user is blocked on a real task, but another route to their goal exists. |
| `minor` | Friction, cosmetics, or a documented workaround that holds. |

**`status` is an ordered lifecycle**: `proposed` → `accepted` → `satisfied`, with
`withdrawn` as the terminal tombstone state reachable from any of the three. `proposed`
means recorded but not yet agreed to; `accepted` means the house has taken the ask on;
`satisfied` means work that CLAIMS to meet the acceptance criteria has landed — see
section 6.4 for the limit on what that claim establishes.

### 6.3 Rules

- `id` MUST be a slug-form ID per section 3.4, with the `REQ-` prefix.
- `date`, `title`, `asked-by`, `impact`, `acceptance` and `status` MUST all be present.
- `impact` MUST be one of the three ordered levels. A missing or out-of-set `impact`
  MUST be flagged, and the flag MUST name the offending value (section 3.5: a register
  whose severity axis can be omitted has no severity axis).
- `acceptance` MUST carry at least one non-empty criterion. Each criterion SHOULD be a
  sentence a Verify row could be written against — a statement that some observation
  would settle. The register does NOT require that such a Verify row exists; that is a
  brief's business.
- `status` MUST be one of the four lifecycle values.
- A `satisfied` entry MUST name at least one `satisfied-by` brief. This is an
  internal-consistency rule about the entry, not a traceability check over the corpus:
  it says an entry may not claim satisfaction anonymously. Whether every requirement has
  work against it, and whether every citing brief resolves, are the corpus-wide checks
  section 6.5 defers.
- `satisfied-by` entries MUST be typed brief IDs per section 3.4. Prose names MUST NOT
  be used.
- Append-only (section 3.1) and tombstone-withdrawal (section 3.3) are inherited: to
  retract an ask, keep the file, set `status: withdrawn`, and explain in the body.
  Deleting the file both loses the record and trips the section 3.2 tombstone check.

### 6.4 What this register does NOT establish

The register records **what was asked for** and **what was claimed to satisfy it**. It
does not observe that the product meets the ask. Specifically:

- A `status: satisfied` entry is an author's claim, not an observation. The observation
  lives in the cited brief's Verify rows and its Evidence, recorded by someone who did
  not implement it.
- An `acceptance` criterion is a sentence, not a check. Nothing in this register runs it.
- A `satisfied-by` reference asserts that a brief was written against the ask. It does
  not assert that the brief covers every acceptance criterion, and a conforming
  implementation MUST NOT present the register as coverage.

A reader who wants to know whether an ask was actually met follows the citation into the
brief and reads its Evidence. The register's job is to make that walk possible, not to
perform it.

### 6.5 The reserved brief citation (`satisfies:`) and the requirement-ref grammar

A brief cites the requirements it was written against with the OPTIONAL `satisfies:`
frontmatter key (`brief-v1.md` §3.2, §3.3). A requirement reference takes one of two
forms:

```
REQ-<slug>              in-repo — a requirement in this tracking root's register
<alias>:REQ-<slug>      cross-repo — <alias> resolved through the existing
                        docs/streams/graph-repos.yaml registry (schema graph-repos-v1)
```

The alias registry is the one already defined for the dependency-graph reference grammar;
a conforming implementation MUST NOT introduce a second alias registry for requirements.
An alias absent from that registry MUST be flagged — the closed-set property is the point
of the grammar.

The citation is parsed, type-checked and shape-validated, and it now feeds the corpus-wide
traceability checks below. Precisely:

- An ABSENT `satisfies:` MUST NOT be flagged, on any brief, ever. No brief is required to
  cite a requirement.
- A PRESENT entry MUST match the grammar above; a violation is a hard flag. A wrong TYPE
  (a scalar where a list is required, a non-string list element) is a parse error.
- A conforming linter MUST emit a NOTICE for a brief carrying the key, so that "parsed and
  traced" is distinguishable from "silently ignored".

**The corpus-wide traceability checks.** These were deferred as reserved at the schema's
first version and land **advisory-first**, in the §4.5 escalation posture: the two questions
a legacy corpus answers wrong land as advisory NOTICEs that change no exit code, and only the
one question a legacy corpus CANNOT answer wrong — a citation of a requirement that was never
defined — is a hard PROBLEM.

- **`orphan-requirement`** (NOTICE) — a requirement whose `status` is `accepted` and which no
  brief's `satisfies:` names. Listed with its `impact` and age, sorted by impact descending
  (the §3.5 ordered axis). A `proposed` requirement is not yet orphan-eligible (the house has
  not committed to it); a `satisfied`/`withdrawn` one is closed. Advisory: it never changes
  the exit code.
- **`untraced-brief`** (NOTICE) — a brief that is `in-progress` or later, in a stream whose
  README declares `traced: true`, and which names no `satisfies:`. The stream opt-in is
  required: a corpus-wide untraced sweep over legacy briefs that predate the register is
  noise (§4.5). Advisory: it never changes the exit code.
- **`dangling-satisfies`** (PROBLEM) — a `satisfies:` naming an IN-REPO `REQ-<slug>` that this
  root's register does not define. Unlike the two NOTICEs it cannot be legacy debt: the
  register is append-only (§3.1, §3.3), so an in-repo id no entry defines can only be a typo
  or a deleted entry. A cross-repo `<alias>:REQ-<slug>` names a register in another repo the
  offline linter cannot read — could-not-check, never dangling.

**What the rollup establishes.** `statusgen --requirements-rollup` walks, per requirement, the
briefs that cite it, each brief's board status, and each brief's Evidence, and reports a
three-state verdict (`satisfied` only when at least one backing brief exists and every one is
`done`; `partial`; `could-not-check`). Like the register itself (§6.4), it reports what was
**authored** — the register and the board rows — not what was **measured**: a `done` backing
brief means the board says the work landed, not that the tool re-ran the acceptance criteria.

These checks reach a consumer only on an `.assay-versions` statusgen pin bump, which is why
they land advisory: an un-bumped adopter is unaffected, and a bumped one gets NOTICEs, not a
red gate, over a corpus authored before the register existed.

## 7. RETRO register (informative — not implemented)

> **Non-normative.** No RETRO register exists in the reference implementation: there is
> no entry directory, no generated view, and no parser. Nothing in this section is
> enforced by any conforming linter today, and section 8 imposes no RETRO requirement.
> It is recorded here as the intended shape of a cadence retrospective, for
> implementations that choose to build one and for a future normative revision.

### 7.1 Purpose

A RETRO is a cadence retrospective (weekly by default) whose inputs are
generated/logged only — no prose-status narrative. A retro that reads its own narrative
measures the narrator, not the system.

### 7.2 Format

```
## R-<slug> — YYYY-MM-DD
<the checklist walked, with numbers>
<the one process change (or "none"), links>
```

### 7.3 Inputs

A retro walks these generated inputs:

- STATUS totals: delta since last retro entry.
- Staleness list: streams untouched since last retro (the rabbit-hole report).
- Gate yield: what reviewers caught; recurring classes graduate to standing rules or
  FINDINGS.
- FINDINGS age: anything stale-flagged longer than one retro is scheduled or explicitly
  parked.
- INTAKE entries still `new`.
- Open tracker bugs.
- Branch and worktree hygiene.
- Knob tuning: Next-up weights, caps, priorities, pause/unpause.

### 7.4 Process-change cap

A retro enacts no more than one process change. A change must displace the current
worst pain to get in; otherwise it waits. The change is recorded as an intake entry,
finding, or brief — never enacted inline.

## 8. Conformance

Conformance is **self-asserted and unaudited** — see `spec/README.md` § "Conformance is
self-declared".

### 8.1 Register conformance

A conforming register:

1. MUST store each entry as a separate file under the entry directory specified in
   section 2.1.
2. MUST treat `FINDINGS.md` / `INTAKE.md` / `REQUIREMENTS.md` as single-writer generated
   views (section 2.2). **Diverges for REQUIREMENTS** — the reference implementation
   parses and validates the entry directory but does not yet generate the view. See
   `spec/README.md` § "Known divergences from the reference implementation".
3. MUST use slug-form entry IDs for new entries (section 3.4), and typed IDs for all
   cross-references.
4. MUST NOT delete existing entry files.
5. MUST use tombstone-withdrawal (flip disposition/resolution, preserve the file) for
   retractions.

### 8.2 Linter conformance

A conforming linter MUST:

1. Flag any duplicate entry `id`.
2. Flag any entry file present in trunk history but absent from the working tree
   (deletion), subject to the advisory limit in section 3.2.
3. Flag any new entry using the legacy numeric ID form.
4. Flag any unresolved finding that makes a brief stale (exclude from Next-up).
5. Flag any malformed `ack:` on an **unresolved** FINDING entry (section 4.4).
6. Flag any INTAKE entry that has been scoped but whose disposition still reads `new`
   or `watching`. **Diverges** — the reference implementation does not implement this;
   it has the inverse alarm, ageing entries that are still `new`. See `spec/README.md`
   § "Known divergences from the reference implementation".
7. Flag any prose reference where a typed ID is expected.
8. Flag any register entry whose format does not match sections 4.2, 5.2 or 6.2.
   **Diverges for FINDINGS** — the reference implementation validates each `affects:`
   entry it finds, but accepts a finding whose `affects:` is empty, which section 4.3
   forbids. The INTAKE half (date and disposition key) holds. See the divergence
   section.
9. Flag any REQUIREMENTS entry whose `impact` is missing or outside the ordered
   vocabulary of section 6.2, naming the offending value (sections 3.5, 6.3).
10. Flag any `satisfies:` entry on a brief that does not match the requirement-ref
    grammar of section 6.5, and NEVER flag its absence.

A conforming linter MUST NOT claim sequence-contiguity or gap detection (section 3.2),
and MUST NOT let a `satisfies:` citation or a REQUIREMENTS entry change an exit code on
any ground other than the two flags above — the traceability checks are reserved
(section 6.5).

A conforming linter SHOULD additionally surface an **advisory** `finding-without-control`
NOTICE for every unresolved `class: recurring` finding whose class has not landed a
control (section 4.5) — either no `control:`, or a `control:` naming a brief that is
not yet `done`. This is RECOMMENDED, not REQUIRED, and it MUST be a NOTICE, never a
hard error: forcing it over an unclassified legacy backlog would manufacture
false-positives (section 4.5). The reference implementation implements it
(`statusgen/findingcontrol.go`, wired into `--lint`).

A conforming linter MUST emit a NOTICE making the reserved status of the requirement
citation visible (section 6.5) — a key that is parsed but never mentioned cannot be told
apart from a key that is ignored. The reference implementation implements the
REQUIREMENTS parser, the `impact` and lifecycle validation, the requirement-ref grammar
and that NOTICE in `statusgen/requirements.go`, wired into `--lint`.
