## What changed

Every verify Evidence PR used to append one line to a single shared
`docs/streams/verify-outcomes.jsonl`, and the forge merges pull requests server-side with no
`merge=union` driver — so each landing turned every sibling Evidence PR touching that one path
`CONFLICTING`, one merge-of-main-and-re-review round trip at a time. `deskevidence
--outcome-record` now commits ONE NEW file per outcome, under
`docs/streams/verify-outcomes/<stream>/<NN>-<YYYYMMDDTHHMMSSZ>-<digest12>.json`, named by
`RecordName` — a pure function of the record's own bytes. Two concurrent landings only ever pick
the same path when they carry byte-identical content (the same outcome), and two identical adds
merge cleanly with no driver. Both `tools/desk` and `statusgen` read the new layout AND any legacy
log line still present, unioned and deduped by content digest, so the transition window needs no
flag day.

`deskevidence` also now refuses (exit 5) any write to a file matching `docs/streams/*.jsonl` —
the class guard, not just this one file's retirement, so a future sink cannot reopen the same
conflict class through a sibling log.

## Upgrade steps

1. **Upgrade your desk tools** (`statusgen`, `tools/desk`) to a build that carries this change —
   the pinned release this migration note ships with.
2. **Run the split once**, from your repo root:

   ```
   statusgen outcomes split --root .
   ```

   Idempotent: it writes one record file per legacy log line (verbatim bytes plus a trailing
   newline) that does not already have one, and writes nothing on a second run. Use
   `--check` first to see what it would do without writing:

   ```
   statusgen outcomes split --root . --check
   ```

3. **Do nothing else.** The legacy log stays in place, frozen — `deskevidence` refuses ever
   appending to it again, so no further line lands there, but nothing deletes it. It is retired
   (deleted, along with its `.gitattributes` `merge=union` line and the
   `statusgen/verifyoutcomes_union_test.go` assertion that pins that attribute) only once every
   open PR that still touches it has landed on your default branch — never while one is open,
   because deleting it under an open PR would turn that PR modify/delete `CONFLICTING` one more
   time, the exact class this migration exists to end.

## Rollback

The previous released binary/skill pin reads only the legacy log — the older reader never opens
`docs/streams/verify-outcomes/`, so a rollback is safe as long as the log itself is still present
(which it always is, until the conditional retirement above). Records this release wrote are
simply invisible to the older reader, not lost; re-upgrading picks them back up.
