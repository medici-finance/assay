Four questions for every kind of change

Correctness checks the result. Security checks the boundaries. Architecture checks our direction. Performance challenges how efficiently we achieve the goal.

Correctness and security exist today. Architecture builds on existing advisory design-fit checks; the expanded architecture and performance profiles below are proposed. They do not add two automatic approval gates.

Existing review

Correctness

Does this change do what it is supposed to do?

Designed to check

  • Behaviour matches the brief, specification and API contract.
  • Edge cases, callers and compatibility remain correct.
  • Concurrency, errors, partial failure, replay and recovery preserve the required result.
  • Tests and evidence support the PR’s actual claims.

How it can do that

Read the exact diff and contract; trace changed values through callers and state transitions. Work through counterexamples. Inspect independently produced test and fail-first evidence, and account for the applicable bug classes.

Useful finding“Retrying after a lost acknowledgement applies the same update twice. Keep a stable operation identity and test replay.”
What a useful result contains

Changed mechanism, reproducing scenario, expected versus actual behaviour, consequence and evidence. Missing checks are explicit. The reviewer reads evidence; isolated test workers execute candidate code.

Existing review

Security

Can this change expose data or let someone do something they should not?

Designed to check

  • Authentication, authorization and tenant/source scope hold at the real effect boundary.
  • Secrets, credentials, logs and exports preserve data custody.
  • Untrusted input cannot become commands, instructions or unauthorized effects.
  • Retries, stale evidence and failure paths cannot bypass controls.

How it can do that

Identify assets, actors and trust boundaries; follow untrusted input to reads, writes and privileged actions. Inspect least-privilege credentials and negative test evidence. Check the lower boundary independently of a friendly UI or upper-layer guard.

Useful finding“The API validates the requested repository, but the executor accepts a different target. Bind authorization to the target actually used.”
What a useful result contains

Concrete attack or failure path, required access, affected asset, enforcement point and a testable repair. Passing a scanner or using two models is not proof that a trust boundary holds.

Proposed extension of design-fit

Architecture

Does this PR move us toward our future state?

Designed to check

  • The change advances or preserves the intended owners and boundaries.
  • It avoids a second source of truth, scheduler, policy meaning or acceptance authority.
  • Dependency direction, pure evaluation and effect custody fit the target.
  • Transitional paths have owners, migration coverage and removal conditions.

How it can do that

Compare the delta and stated intent with the pinned future-state design, approved decisions and applicable migration stage. Trace ownership and dependency changes; inspect consumers and recovery. Reuse fitness tests, then explain the direction and a feasible alternative.

Useful finding“This adds a second scheduler, moving us away from one cell controller. Express it as an admitted cadence occurrence, or record a bounded transitional exception.”
What a useful result contains

Advances / preserves / moves away / cannot assess, with the specific target passage, changed mechanism, tradeoff and retirement or decision need. Preserving a sound design is valid. A future proposal alone cannot impose an unrelated migration or a new blocker.

Proposed profile

Performance & efficiency

Can we achieve the same goals with less work and less undue contention?

Designed to check

  • A better algorithm or data structure could reduce total work at realistic sizes.
  • Repeated scans, subprocesses, forge reads and model context are avoidable.
  • Batching, incrementality or caching help without breaking freshness or recovery.
  • Locks, serial work and unbounded concurrency create unnecessary contention.

How it can do that

Restate the tool’s design goals, workload and constraints. Derive where time, CPU, tokens, calls and memory multiply. Compare a concrete alternative and its tradeoffs. Propose a discriminating experiment; use controlled base/head evidence when impact needs proof.

Useful finding“Every item reparses the entire history: work grows as items × history. Build one revision-scoped index per run, preserve freshness and errors, then compare small and large workloads.”
What a useful result contains

Current approach, alternative, cost model, equivalent-result conditions and validation plan. Label a design opportunity, measured result, existing budget violation or inconclusive. A promising algorithm is useful before measurement; it is not yet a proven speedup.

Make the extra reviews earn their place

Run a bounded, advisory pilot. Compare existing reviews with the same reviews plus each new profile on frozen cases, with equal declared budgets. Independently judge additional important findings and false positives.

Measure runs, tokens, CPU, wall and queue time, forge/GH calls, human effort, repair rounds and cost per validated additional finding. Show mean and P95 over comparable cohorts, sample counts and missing coverage. Pair total cost and lead time per verified brief with preserved quality.

Observe → confirm → deduplicate issue → bounded repair → draft PR → independent review & verification → reassess after exposure

Later cadence and repair authority use the existing supervised workflow and future single cell controller. A report cannot authorize its own merge, deployment, new gate or architectural target.
