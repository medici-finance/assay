### A. Publishable form of the cohort evidence (Task 1 hold)

**Why.** Task 1 required the reduced fixture as exact matcher bytes, nonmatches included, with no silent redaction. The implementer's 2026-10-21 snapshot had 21 pages and 2076 records. The repository's withheld-content sweep fails on those exact bytes: 37 sweep entries fail across 634 records on all 21 pages, including 51 head refs and 7 of the 13 cohort members. Exact bytes therefore cannot be committed to this public repository. Neither silently redacting them nor claiming an exact replay from the committed files is truthful.

**Default taken: a hash-bound inventory in the repository, with the exact-bytes replay held privately by each runner.**

- `candidate-inventory.json` replaces the planned `candidate-pages.json`. It is committed and has one entry for every scanned record, in page-and-position order. Matches and nonmatches are both included, and nothing is dropped. Each entry holds:
  - page, position and PR number;
  - state, draft, merged_at, merge_commit_sha and head.sha;
  - `kept_sha256`, the SHA-256 of that record's kept fields (number, state, draft, body, merged_at, merge_commit_sha, head.sha, head.ref) in the pinned serialization below;
  - `files_sha256`, for every record whose file list any matcher or classifier in this brief's flow reads (every trailer or backfill candidate), in the same pinned serialization; it is `null` for a record whose file list is never read.

  **Pinned serialization** (amendment A, security review advisory A4). A record is hashed as `{"number":…,"state":…,"draft":…,"body":…,"merged_at":…,"merge_commit_sha":…,"head":{"sha":…,"ref":…}}`, keys in exactly that order, and a file list as a JSON array, in forge order, of `{"filename":…,"status":…,"previous_filename":…}` (the fields `prFile` decodes). Both are UTF-8, encoded with Go `encoding/json` `Encoder` with `SetEscapeHTML(false)` and no indentation; the encoder's trailing newline is stripped, so the hash covers no trailing newline. Fields are hashed as decoded into the existing `ghPull` and `prFile` structs, whose fields are plain strings. A JSON `null` and an empty string therefore both serialize as `""` (for example `body`, `merged_at`, `merge_commit_sha` and `previous_filename`). The hash binds exactly what the matchers read, and the matchers cannot tell `null` from `""` either. It does not bind that distinction, and no row claims it does (correctness review round 2, advisory). Strings are the values `encoding/json` decoded from the response (invalid UTF-8 already replaced with U+FFFD), so rows 11 and 14 recompute the same bytes. A committed known-answer vector pins the bytes: a synthetic record whose body contains `<`, `>`, `&`, a non-ASCII character and an invalid UTF-8 byte, and a synthetic file list, each with its expected serialization and SHA-256.

  `body` and `head.ref` appear only inside that whole-record hash, never as a per-field hash or excerpt. Per page, the inventory records the request parameters, record count, decoded-response SHA-256 and terminal short-page evidence. It also records the cutoff, the collection limits, the actual byte totals, and a `snapshot_sha256`. The snapshot digest is the SHA-256 over one `<page>\t<position>\t<number>\t<kept_sha256>\n` line per record, in inventory order. The inventory also carries `eligible_sha256`, the SHA-256 over one `<number>\t<kept_sha256>\n` line per *eligible* record (merged at or before the cutoff), in ascending PR-number order. Page and position are excluded because a later walk cannot reproduce them.
- `candidate-cohort.json` keeps the per-member disposition, reason and evidence bindings: merge SHA, the member's `files_sha256` (the same value as in the inventory), and which matching path or paths selected the member. For each member it adds a **synthetic stand-in**, labelled as synthetic. The stand-in holds the member's inventory identity fields, its body/ref link-trailer lines (`Brief:`, `Authors:`, `Issue:`) verbatim, and the literal backfill form the matcher hit (`derived-board/07` or `derived-board-07`). Nothing else from the body or ref is copied. For each member, the cohort also commits the file list verbatim in the pinned form: every `filename`, `status` and `previous_filename`, in forge order. CI recomputes the member's `files_sha256` from those bytes, so the committed list is bound to the inventory. The file lists are sweep-checked and manually inspected like the rest of the committed bytes. If any path of a member fails the sweep, that member's file list becomes the bare marker `held` and its CI verdicts are could-not-check, never stubbed. The real classifier runs over the committed lists in row 13. If the classifier needs anything for a member beyond its file list, such as a patch or head content, that read is either committed under the same sweep-and-hash rule or the member's verdict is held could-not-check. Stand-ins and file lists drive the CI rows. They are not the replay and must never be described as one. If a member's stand-in cannot pass the sweep, its stand-in is replaced by the bare marker `held` and that member's CI verdicts are could-not-check. The member's inventory entry and disposition stay, so nothing is dropped. The committed files never say which field, line or sweep entry caused the hold (security review advisory A3); that detail stays with the runner. The residual disclosure, that some trailer line of a public PR is held, is accepted: those lines are already public on the forge.
- **The exact-bytes replay is private.** Each runner keeps the reduced exact-bytes replay outside the repository. The replay is never committed, attached to an issue or PR, or pasted into a comment. A replay declares one of two kinds, and row 14 refuses one that declares neither:
  - **Captured.** The reduced bytes of the original walk, received privately from the implementer: every inventory record, all 2076 of them including open and post-cutoff PRs, in page-and-position order. Row 14 binds it to the full inventory by per-record `kept_sha256` and by `snapshot_sha256`.
  - **Rebuilt.** Written by row 11 from a fresh walk, so a nonimplementer can build it from the forge without the implementer's private copy. Pagination has moved since capture and row 11 vouches only for eligible records, so a rebuilt replay holds exactly the eligible records, keyed by PR number. It also holds the file list of every eligible record whose inventory `files_sha256` is non-null, read by row 11's bounded file-list read (below). Row 14 binds it to the eligible subset of the inventory by per-number `kept_sha256`, by `eligible_sha256` (never `snapshot_sha256`) and by per-record `files_sha256`. A rebuilt replay with a missing, extra, duplicate or ineligible record, or a missing file list, is a named could-not-check.

  Either way the source is never trusted: row 14 binds the replay before the matcher runs over it. Cohort members are all eligible, so both kinds support the same cohort derivation. The replay carries each candidate's file list beside its record; row 14 checks every file list against the committed `files_sha256` before any classifier reads it, and a mismatch or a missing file list is a named could-not-check (security review F2). The matcher, classifier and flow consume only fields projected from a hash-verified record or file list and re-serialized in the pinned form; no other replay field reaches them. The comparison is one function in the test package, which takes an inventory path, a replay path and an output writer, and prints the `REPLAY` marker only on success. Row 14 calls it with the opt-in path. Row 15 calls the same function, not a copy, with synthetic files and asserts the marker in its output. Row 15 therefore proves that row 14's own comparison fails closed in CI (security review F1; correctness review F2). The roughly 9.1 MB body budget in Task 1 now applies to the private replay. The committed inventory is a few hundred kB.
- **The sweep and manual inspection apply to the committed bytes.** That means the inventory, the cohort with its stand-ins, and the provenance receipt. The per-page checklist in `candidate-provenance.md` still accounts for every PR ID on every page, together with its committed form (hash-only, or hash plus stand-in) and the sweep result over the committed files. It never names or quotes what the sweep matched in the private replay; it may give only counts of affected records. An independent reviewer still checks that every scanned record is accounted for before publication.
- **Row 11 compares hashes.** Its two fresh walks compare each eligible record's recomputed `kept_sha256` against the inventory. A mismatch or a missing record keeps its version-5 meaning: checked-failed for current membership, and could-not-check for changed historical bytes. The private replay is not needed for this comparison.
  - **One bounded file-list read** (correctness review round 2, F1). Task 3 allows row 11 only collection GETs on `/repos/medici-finance/assay/pulls`. Amendment A adds exactly one more read: `GET /repos/medici-finance/assay/pulls/{n}/files?per_page=100`, read-only and paginated through its `Link` header. It is allowed only after both walks agree, and only for an eligible PR whose inventory `files_sha256` is non-null. At this snapshot that is the 13 cohort members, and it is never more than the eligible count. Each file list is read once and must match its `files_sha256`. A mismatch, an unreadable list or a list cut off by the forge's file cap is a named could-not-check, and no file list is accepted on trust.
  - **Its bounds.** It uses the same origin, redirect refusal, bounded `httpDoer` and no-retry rule as the walks. Each PR gets at most 30 file-list pages, the forge's 3000-file cap. Every file-list request and decoded byte counts toward Task 3's existing ceilings: 200 requests, 8 MiB per decoded response, 512 MiB total, and 180 seconds. The two walks use about 42 requests and the 13 lists about 13 more. Before first contact, row 11 prints the file-list endpoint pattern, the number of PRs it will read and their numbers. Any other endpoint stays refused. That includes a file-list read for a PR outside that set, `/pulls/{n}` detail, contents, commits and every write.
  - When every eligible record and every file list matches, row 11 may also write a rebuilt replay (eligible records and those file lists, keyed by number) to a runner-supplied path outside the checkout (`ASSAY_COHORT_REPLAY_OUT`). It must refuse any path inside the working tree. Both `ASSAY_COHORT_REPLAY_OUT` and row 14's `ASSAY_COHORT_REPLAY` are made absolute and symlink-resolved (for an output path, the deepest existing parent) and compared with the symlink-resolved worktree root; a path that resolves inside is refused, even when its lexical form is outside (security review advisory A2).

**What does not change.** "No silent redaction" still binds: every record is present, every withheld field is bound by hash, and this section declares the form openly. The matcher is proven against the exact bytes only by the opt-in row 14, never by stand-ins or by CI. The binding that row 14 relies on is proven fail-closed in CI by row 15. Verify row 10 (the #735 five-path check) and the #1196-against-#1062 positive-control scoping are unchanged.

### B. Mention-only candidates on the historical backfill path (Task 2 hold)

**Why.** The backfill path selected 13 merged candidates. Eight of them, #153, #194, #1006, #1251, #1358, #1457, #3787 and #3794, match only because their bodies mention `derived-board/07`. None of them authors or delivers brief 07, and none fits the full, partial, authoring or Evidence-only dispositions. `matchBackfillPRChecked` tries candidates newest first and takes the first one that is not authoring-only for this brief and not declared partial. Driven through that path as Task 4 requires, it would select #3794, the authoring PR of *this* brief, as brief 07's implementation witness instead of yielding in-progress. Every one of the eight carries a link trailer that does not name brief 07:

| PR | Own link trailer |
|---|---|
| #153 | `Brief: mistake-proofing/01` |
| #194 | `Brief: derived-board/05` |
| #1006 | `Brief: desktools-go-git/04` |
| #1251 | `Brief: graph-execution/01` |
| #1358 | `Brief: derived-board/03` |
| #1457 | `Issue: #1339` (no `Brief:`) |
| #3787 | `Issue: #2703` (no `Brief:`; it edits brief 07's `delivery:` list) |
| #3794 | `Authors: derived-board/10` (no `Brief:`) |

**Default taken: a fifth disposition and one backfill selection rule.**

- **Disposition `mention-only`** (different brief). The candidate names this brief only in prose. Its own link trailer declares a different brief, an issue, or authoring. Its reason must quote that trailer and state that the candidate delivers none of brief 07's obligations. The evidence is the trailer line and the file-list hash.
- **Backfill rule (production, `statusgen/briefauthoring.go`).** The historical fallback exists for trailerless history (brief 07 facts). A backfill candidate is *trailer-era* when its body carries at least one link trailer (`Brief:`, `Authors:` or `Issue:`) outside fenced code. A trailer-era candidate is never an implementation witness for a brief unless one of its `Brief:` values reduces, via `canonicalBriefKey`, to that brief's key. `matchBackfillPRChecked` walks past it in both branches, with and without the classifier seam.
  - **One shared predicate.** The walk-past decision is not restated. `attributeCandidate`'s trailer arms (`statusgen/autoflip.go`) move into one predicate that takes the parsed `Brief:` keys and trailer count. `attributeCandidate` calls it after its unchanged bulk-migration check, so autoflip's behaviour stays the same. Backfill calls the same predicate. A walk-past verdict (a `Brief:` naming another brief, or `Authors:` only) walks past. A credit verdict, or the unattributable verdict for several `Brief:` values that include this brief, goes to the existing authoring, Evidence-only and declared-partial reader. A body with no link trailer keeps the version-5 behaviour. Backfill adds one arm, and only backfill uses it: the predicate's unattributable verdict for "no `Brief:`" walks past when the body carries an `Issue:` trailer. `Issue:` is the one addition to the fence-aware trailer grammar (`parseBriefLikeTrailers`), and it is returned as a separate count. The `Brief:`/`Authors:` count that `bulkMigrationReason` reads does not change, which row 16 asserts.
  - **Order: the file list is read first.** With the classifier seam wired, every candidate the walk reaches has its file list read through the existing seam before the walk-past decision. An unreadable file list on any reached candidate, including one that would be walked past, still ends the search unresolved, exactly as now: no witness, no continued search, an unknown result. A walk-past never skips a read that would have stopped the search.
- **Properties.**
  - `backfillCandidates` membership is unchanged: the cohort still lists all 13.
  - Trailerless historical PRs keep the version-5 behaviour.
  - A candidate whose `Brief:` names this brief is still governed by the authoring, Evidence-only and declared-partial reader.
  - Precisely what the rule does (security review advisory A1; correctness review F3). It never adds a candidate, so a brief with no backfill candidate gets none. It does **not** only remove witnesses. The walk continues after a walk-past, so an older candidate the old walk never reached can become the witness: an older trailerless PR, or an older trailer-era PR naming this brief. That is the false-older-witness class this brief exists to catch. The defence is the cohort coverage join (rows 2 and 3), not this rule: an exposed older candidate without a disposition fails coverage by name. A reached candidate whose file list cannot be read still ends the search unknown.
  - Observation, not a guarantee: the correctness review measured the rule over all 530 briefs. 171 lose their newest backfill candidate, and in every one of those the walk ends with no candidate at all. No measured brief gained an older witness. Future history can, and row 13's neighbours test that case.
  - A trailer-era PR that truly delivered a brief without naming it in `Brief:` is not credited by backfill. Its remedy is the one brief 07 already provides: add the trailer to the merged PR, or a delivery declaration.
- **Deviation from the routed default, stated so it can be declined.** The routed default excluded a candidate whose own `Brief:` trailer *or whose file list* names a different brief. Checked against the eight, that covers only six. #1457 has no `Brief:` trailer and touches no brief file. #3787's file list includes brief 07's own file. Widening the trailer test to `Issue:` and `Authors:` covers all eight. The file-list arm is not adopted: no member needs it, and it would exclude a real trailerless delivery that also edits another brief's file.
- **Proof.** New Verify row 13 proves the following:
  - through the backfill path, #3794 yields in-progress with no witness;
  - the whole cohort yields in-progress, with each of the eight walked past by its own trailer;
  - disabling the rule in an isolated test seam makes #3794 the witness again;
  - an older trailerless candidate behind a walked-past one is reached and selected, and the coverage join names it;
  - an unreadable file list on a reached candidate, walked past or not, ends the search unknown with no witness.

  Task 2's ban on new production semantics is lifted for this one rule only. Declarations, generated cells and historical trailers stay untouched.

**What does not change.** Verify row 10 and the #1196-against-#1062 positive control (row 5) are unchanged. The five partial declarations stay byte-identical. S-delivery still has no declared semantic owner: the rule sits beside the existing authoring exemption at the same seam and does not claim ownership.
