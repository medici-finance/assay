# One verdict from the verification run to the board

When a verifier records a run, the evidence writer, queue and flip command should agree on what happened. A passing row can belong to a run that is still blocked on closure. Issue [#6002](https://github.com/medici-finance/assay/issues/6002) reports that the writer accepted an overall `pass`, leaving the board unable to classify that brief. Issue [#5827](https://github.com/medici-finance/assay/issues/5827) reports the converse granularity problem. Three failed or blocked records omitted the held rows, so the next verifier could be sent to rerun the whole table.

The verification owner is responsible for the record meaning in `statusgen/evaluation`. The desk tools own publication and wake scheduling. The first delivery is a public-source change. The following are proposed milestones for the existing [tool-refactoring/05](../brief-05-share-outcome-decoding-and-reduction-between-verification-producers-and-readers.md) and its consumer work. They carry no stage transitions.

| Milestone | Observable improvement | Acceptance and measure |
|---|---|---|
| 1. Writers and readers understand the same overall result | A verifier catches a row result entered in the overall field before spending a forge operation. A recognized verified spelling runs the existing closure checks. | Run the public vocabulary matrix and the `deskevidence` command tests. Each recognized spelling must reach its expected category. A row-only, unknown or missing value must produce exit 5, zero admissions and zero writes. Record disagreements per case before and after. |
| 2. Held runs identify the work still owed | A run that passes every row and waits on human closure, a run with one unavailable row, and a later diagnostic on an already verified brief reach their respective queues. The verifier can see which rows genuinely need another run. | Complete /05’s row reduction and route it into [tool-refactoring/10](../brief-10-migrate-evidence-publication-to-bounded-deltas-and-typed-outcome-admission.md). Replay those three cases plus suffixed row IDs, partial coverage, divergent base/head results, malformed legacy rows and future timestamps through the real writer and readers. Count wrongly redispatched rows, lost holds and incorrect closures. Require zero in the fixture cohort. `statusgen/37` owns content-bound writer adoption; `desk-tools/46–47` own evidence reuse and continuation. |
| 3. A released verifier completes the same cases in a Kubernetes-hosted desk | An operator can see the admitted revision, published result and the next action agree after an interrupted landing and retry. | Use [tool-refactoring/11](../brief-11-qualify-the-joined-tool-flow-and-prepare-consumer-by-consumer-retirement.md) to qualify a pinned producer and consumer pair against single-repo and split tracking/delivery examples. Capture tool and runner image versions, per-case expected versus actual bucket, required rows rerun, duplicate records and incorrect flips. Repeat across the intended upgrade pair, including an older reader. Require zero contradictory buckets or incorrect flips. Record unavailable capabilities explicitly and qualify a second deployment profile separately. |

The source head for milestone 1 is the mismatch in `statusgen/awaiting_bucket.go` and the writer in `tools/desk/cmd/deskevidence/outcomerecord.go` at `185b7ee7e`. The former calls `classifyOutcome`; the latter decoded a submitted outcome without checking the recognized vocabulary. Independent closure, source binding, actor checks and existing protections on historical evidence apply throughout. A correction to an old record follows its existing repair process. An operator and independent verifier supply deployment evidence for milestone 3.
