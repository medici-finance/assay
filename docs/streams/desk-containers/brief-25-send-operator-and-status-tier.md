# Brief 25 — `cellctl send` for the local operator, and Tier A status

## Context
files:
- `tools/desk/internal/comms/` — the lane ACL: an `operator` sender class with its own verbs
- `tools/desk/cmd/commsgw/` — operator identity derivation on the local socket; Tier A responder
- `tools/desk/cmd/cellctl/send.go` (planned), `send_test.go` (planned); `cobra.go` registers `send`
- `plugins/assay/skills/{the-desk,pr-review-desk,verify-desk,worker-desk,intake-desk}/SKILL.md` — one rule for `operator` messages, pointed at a shared reference
- `plugins/assay/references/operator-messages.md` (planned)
- `docs/cellctl-comms.md`
- `changelog/desk-containers-25-send-operator.md` (planned)

single-point-of-failure: operator identity is derived from local-socket custody — behind it, the cell signing key on every message, the gateway's authoritative ACL re-check, and the desk's own rule that an operator message is attributed and may be declined.

facts:
- **Operator keys are shared with desk-containers/15.** Operator public keys live in the comms trust store as operator-tagged entries; brief 15's signed plan approvals verify against the same entries. Whichever brief lands first adds that trust-store shape.
- **Sender classes are decided by authenticated identity, never by content.** In this brief there are two: `desk:<role>` (today) and `operator`. A message is `operator` only when it arrives on the cell's local socket from the socket-owning OS user, is signed with the cell key, and is sent by `cellctl send` (which sets no identity field: the gateway derives it). Any identity-like field in the payload is ignored and logged.
- **Tier A** is `cellctl send <cell> <role|all> --ask status`. The gateway answers it from the desk-containers/20 status document for the named roles, rendered by code. No model and no desk session sees the request, and the reply is the desk-containers/15 result. This is the default and only form of `--ask`.
- **Operator messages** (`cellctl send <cell> <role> --verb note|instruct < text`) are delivered to the desk's lane as `from: operator`. The desk acts only within its normal skill rules and may decline. Every send and delivery is in the existing comms audit trail.
- **Layers** (rule 10; each fails for a different reason):
  1. gateway identity derivation plus signature check (refuses an unsigned or foreign-key message);
  2. the compiled lane ACL (refuses a verb the class may not send);
  3. the desk's skill rule (attributes, may decline, never treats message text as overriding its skill);
  4. the audit trail, reviewed by `doctor` (desk-containers/21) for operator messages with no delivery record.
- No external sender, no network listener, and no free-text-to-model path exist in this brief. Those are briefs 26 and 27.

## Human decision
Should the cell's comms service accept a new kind of sender, the local operator, who may send instructions to a desk, and answer "status" questions by code?

Today only desks can message desks. This adds the person running the cell as a sender. They are identified by owning the local socket and by the cell's signing key, never by anything written in the message. Status questions are answered from the cell's status document by code, with no AI reading the question. Instructions arrive at the desk marked as coming from the operator, and the desk may decline them.

Options:
1. **Approve as designed** — an operator lane with `note` and `instruct` verbs, plus code-answered status. Work proceeds.
2. **Approve status only** — ship Tier A and the `note` verb; leave out `instruct` until there is operating experience. The brief drops the instruct verb.
3. **Reject** — keep comms desk-to-desk only; `send` is not built.

Default if no answer: none — blocks until answered.
