facts:
- **Pinned versions, re-established at implementation.** Pin CloudNativePG 1.30.1, the Barman Cloud Plugin v0.15.1 and the operand image `ghcr.io/cloudnative-pg/postgresql:18.6-system-trixie`, pinned by digest in `spec.imageName`. 18.6 is the same PostgreSQL version as brief 26's local image, so the migration is same-major and same-minor. Before writing, check each pin and every field below against that release's CRDs and docs, not against this brief or memory. If a newer patch release is out, use it and record it in the PR body. The plugin requires cert-manager. Installing the operator, the plugin and cert-manager is cluster-scoped, so the component does not do it. `docs/postgres.md` (planned) names the versions and lists those installs as prerequisites, each to be done by the adopter's own GitOps or by hand.
- **Shape: an opt-in component, as in brief 12.** Brief 06's base stays untouched. `containers/k8s/components/postgres/` is a `kind: Component` holding namespaced resources only. The reference overlay `containers/k8s/overlays/postgres/` lists the base plus the component. Storage class, storage size, instance count, anti-affinity, bucket, endpoint and the list of cells are overlay values, by brief 06's template/overlay boundary. Nothing Argo-specific or Flux-specific goes in the component, so briefs 13 and 14's adopter overlays can add it with one `components:` line.
- **Cluster.** Name `assay-pg`. `instances: 3` by default. The doc states that three pods on one node or one zone do not survive losing it (doc 14 line 11): for real HA the overlay sets required pod anti-affinity on a topology key with real failure domains. `enableSuperuserAccess: false`; no application ever uses the superuser. Storage comes from a PVC template whose class is an overlay value. `spec.plugins` names `barman-cloud.cloudnative-pg.io` with `isWALArchiver: true` and `barmanObjectName: assay-pg-store`. TLS is CNPG's default server TLS. A client sets `sslmode=verify-full` and `sslrootcert` to the CA from the cluster's CA Secret; the doc shows how to extract it. A client that sets those is protected; CNPG's default `pg_hba` ends in a `host` (not `hostssl`) password rule, so the server would still accept a client that does not. The component therefore adds a `hostnossl all all all reject` rule through `spec.postgresql.pg_hba`, provided the pinned release orders user rules ahead of its own final rule; that ordering is re-established from the release docs at implementation, with the same caveat as the `samerole` alternative below, and a release that does not allow it is recorded in the PR body. Exposing the `-rw` Service to host cells outside the cluster (port-forward, a LoadBalancer through `managed.services`, or running the cell in-cluster) is an operator choice. The doc lists the options and ships none as a default; its LoadBalancer example always sets `loadBalancerSourceRanges`. A second, opt-in component, `containers/k8s/components/postgres-networkpolicy/`, holds one `NetworkPolicy` that admits the desk namespace and the CNPG operator's status port to the cluster's pods and nothing else, so an adopter without it knows any pod can reach `assay-pg-rw`.
- **Per-cell database and role: standalone `Database` and `DatabaseRole` objects.** One pair per cell, named from brief 26's mapping (`example-cell` maps to `cell_example_cell`). The `DatabaseRole` sets `login: true`, `superuser: false`, `createdb: false`, `createrole: false`, `replication: false`, `bypassrls: false`, a `connectionLimit`, `passwordSecret` naming a `kubernetes.io/basic-auth` Secret, and `databaseRoleReclaimPolicy: retain`. The `Database` sets `owner` to that role, `databaseReclaimPolicy: retain`, and any `extensions:` the consumer needs. Removing a cell from Git therefore leaves its role and data in place for the operator to retire by hand.
  - Alternatives set aside: `Cluster.spec.managed.roles` puts every cell's role in the one shared `Cluster` object, so each cell add or remove edits the cluster definition, and a role has no reclaim policy of its own there. An init Job is imperative and nothing reconciles it.
- **Per-cell isolation needs one SQL step.** The 1.30.1 `Database` CRD has no field for database-level privileges, re-established from the CRD at implementation. PostgreSQL grants `CONNECT` and `TEMPORARY` to `PUBLIC` on a new database. The migration script and the doc's add-a-cell procedure therefore run `REVOKE CONNECT, TEMPORARY ON DATABASE <db> FROM PUBLIC` through `kubectl exec` into the current primary (from the Cluster's `status.currentPrimary`) as the local `postgres` user. That uses the in-pod socket and needs no superuser network access. Brief 26's `check-isolation.sh` gains a `--kubectl <namespace>/<cluster>` mode and detects a cell added without the step. Object ownership is the second layer, as in brief 26. This is isolation at the database layer only, and the doc says so in brief 26's words. The credential layer is no stronger here: every cell's role Secret sits in one namespace, so anyone who can read Secrets there can read every cell's password, and a host cell's pgpass file for the cluster is readable by every other host cell on the same OS user (brief 26's credential-layer fact). The cluster also has a superuser path of its own: `kubectl exec` into the primary as the in-pod `postgres` user (the path this brief's own `REVOKE` step uses) is a superuser session over the local socket, whatever `enableSuperuserAccess` says, and `pods/attach` and `pods/ephemeralcontainers` (a debug container in the pod) reach the same socket. The doc states all of this and points to the remedies: on the host side, brief 26's (each must also withhold the cluster kubeconfig that holds the verbs below); on the cluster side, RBAC that keeps to the operator alone, in the namespace, `get`/`list`/`watch` on Secrets, `create` on `pods/exec` and `pods/attach`, `patch`/`update` on `pods/ephemeralcontainers`, and pod creation. A cell's identity (an in-cluster ServiceAccount, or the kubeconfig a host cell uses for a port-forward) holds none of them. Verify row 9 checks this for the restore identity and a cell identity. An alternative to re-establish, not adopt blind: `spec.postgresql.pg_hba` with `samerole` rules. Whether user rules can deny before CNPG's own final rule depends on the release's rule ordering. <!-- graph: encoded desk-containers/26→desk-containers/27 -->
- **Secrets out of band.** Each cell's role Secret (`kubernetes.io/basic-auth`, `username` equal to the role name) and the object-store credential Secret are created by the operator, by hand or through External Secrets, Sealed Secrets or SOPS; the doc names these options without depending on any. `secret.example.yaml` shows the shapes with placeholder values only, and it is not in `resources:`, so the build never contains it. Example values: endpoint `https://s3.example.com`, bucket `s3://example-bucket/assay`. The doc requires the object-store credential to be scoped to that one bucket and prefix (read, write and list there only), because the bucket holds every cell's data and WAL.
- **Backups.** `ObjectStore` `assay-pg-store` with `endpointURL: https://s3.example.com`, `destinationPath: s3://example-bucket/assay`, `s3Credentials` naming the out-of-band Secret's keys, and a `retentionPolicy` (default `30d`, an overlay value). WAL archiving is continuous, so recovery is point-in-time. The `ObjectStore` sets the plugin's `data.encryption` and `wal.encryption` (server-side encryption) where the pinned release supports them, re-established from the plugin docs at implementation; the doc says that backups otherwise sit in the bucket unencrypted at the object-store layer. One `ScheduledBackup` runs daily with `method: plugin` and `pluginConfiguration.name: barman-cloud.cloudnative-pg.io`; CNPG's schedule takes six fields, seconds first. The recoverable point is the last archived WAL segment, and the doc states CNPG's archive timeout as the bound on loss for a quiet database (re-established from the release docs). It claims no zero loss and says replicas do not replace backups (doc 14 lines 11 and 44).
  - Set aside: the in-tree `.spec.backup.barmanObjectStore`, deprecated in 1.30 and to be removed in 1.31.0; and `volumeSnapshot` backups, which need a CSI snapshot class the example cannot assume.
- **Recovery leaves cells unable to connect.** The doc's restore procedure creates a new `Cluster` that bootstraps by recovery from the object store, through `externalClusters` with the plugin, `barmanObjectName` and `serverName`. Before applying it, the operator sets `login: false` on every cell's `DatabaseRole` in Git. Recovery restores role attributes as of the backup, and the CNPG operator then re-applies Git's `false`. So no cell connects to the restored cluster until the operator has completed the consumer's reconcile procedure (graph-execution/16 operator incarnation; doc 14 line 56) and flipped `login` back. That is the local `NOLOGIN` gate from brief 26, carried over. The consumer's paused-on-mismatched-incarnation check (graph-execution/19) is the independent second layer.
- **The local-to-CNPG migration (doc 14 line 15; doc 15 line 62)** is a runbook in `docs/postgres.md` (planned) plus `migrate-cell.sh`, which handles one cell at a time:
  1. **Pin compatible versions.** The script refuses unless the source and target server major versions are equal and the target minor is at least the source minor. Every `pg_extension` row in the source database must be declared in the target `Database`'s `extensions:` and be available on the target image.
  2. **Quiesce admission.** `cellctl down <cell>`, then brief 26's `provision-cell.sh --cell <cell> --disable-login`. The script refuses while `pg_stat_activity` shows any session for the role.
  3. **Declare the recovery point.** One final `backup.sh` run after quiescing. Its manifest (UTC start time and sha256) is the declared recovery point and is written to the migration log. Rebuild path: if the source cannot be dumped, the consumer rebuilds from canonical sources (graph-execution/19's reconstruction; doc 14 line 46) with admission paused. The script does not attempt that rebuild.
  4. **Migrate, never as the superuser.** The target `Database` and `DatabaseRole` exist with `login: false`, and the target `Database` already carries the source's extensions (step 1), so the operator creates them, not the dump. The dump is cell-controlled input, so the data load follows brief 26's restore rule: its session authenticates as the one-shot non-superuser `assay_restore`, created through `kubectl exec` as the in-pod `postgres` user with brief 26's attributes (`NOINHERIT`, `CONNECTION LIMIT 1`, `VALID UNTIL` the run's deadline, its password as a client-computed verifier with brief 26's session `SET`s, including `pg_stat_statements.track_utility = off`), with one membership, in this cell's role, granted `WITH INHERIT FALSE, SET TRUE`, plus `CONNECT` on the target database. A trap tears it down with brief 26's ordered steps, run through `kubectl exec` as the in-pod `postgres` user: `ALTER ROLE assay_restore NOLOGIN` first, then `pg_terminate_backend` for its sessions, then `REASSIGN OWNED BY assay_restore TO <cell role>` and `DROP OWNED BY assay_restore` in the target database, then `DROP ROLE`; any failed step exits non-zero naming the step, and the run reports failure. Without that order, cell `CHECK`-constraint code in the dump could grant to `assay_restore`, give it an object, or set its password, and a `LOGIN` member of the cell role would survive the target's `login: false`. The data load runs `pg_restore --role=<cell role> --no-owner --exit-on-error --single-transaction`, with the dump's `EXTENSION` entries left out of the restore list. A restore as `-U postgres` is forbidden: a cell-owned `SECURITY INVOKER` function in a `CHECK` constraint would run as the superuser, and `SET ROLE` alone does not stop it because the function can `RESET ROLE`. How `assay_restore` authenticates (for example from the host through a port-forward to the `-rw` Service with TLS and a one-shot 0600 passfile in a `mktemp -d` directory the trap removes) is re-established against the pinned release and recorded in the PR body; never an argv or environment value. The data load's port-forward runs under a separate kube identity, passed as `--load-kubeconfig`, that holds only `get` on pods and `create` on `pods/portforward` in the namespace; the operator's own kubeconfig runs the `kubectl exec` steps. The kind overlay creates that restore identity as ServiceAccount `assay-pg-restore` with a Role granting exactly those, and the doc gives the same Role for adopters. The script then applies the per-cell `REVOKE` as the in-pod `postgres` user.
  5. **Validate.** The sorted data-only text of the dump must equal that of a dump taken from the target, as in brief 26's drill. Extension lists must match. The consumer's schema-migration version, if its table exists, must be equal. Any mismatch stops the run before the switch.
  6. **Switch endpoints.** `cellctl set <cell> CELL_DB_DSN=<target DSN>`, with TLS settings, and `CELL_DB_PASSFILE=<new pgpass file>`. The source role stays `NOLOGIN`, so a cell still pointed at the old server fails closed rather than writing to the stale copy. The source database is kept; retiring it after a retention window is a separate, manual operator step.
  7. **Reconcile outstanding effects.** This is the consumer's procedure (graph-execution/16 and /19), run before any reopen. If the cell has no consumer schema yet, the log records "nothing to reconcile: no consumer schema".
  8. **Reopen admission.** Set `login: true` on the cell's `DatabaseRole` in Git, then `cellctl desk` / `cellctl up`.
  - Never move a live local data directory onto a network volume and call that a migration (doc 14 line 15).
  - Set aside as the primary path: `bootstrap.initdb.import` (microservice/monolith). It runs only when a `Cluster` is created, so it cannot add a cell to a running cluster. It also needs network reach from the cluster to the host's loopback-only server. The doc mentions it as an option for a first, all-cells cutover into a new cluster.
- Not a core-system brief, but its credential custody is human-gated (see `gate-why`). The single control between a migrating cell and a split write is the source role's `NOLOGIN`. The target role's `login: false` until reopen is the second, independent layer; it trips on a different server. The single control between a migrated dump and the target's superuser is that the data load authenticates as `assay_restore`; the second layer is that `assay_restore` is a non-inheriting member of the one cell role only. Between cell code and a surviving restore login, the single control is the trap's ordered teardown; `VALID UNTIL` is the second layer, and the target role's `login: false` does not depend on either. Between a cell identity and the in-pod superuser, the single control is RBAC withholding `pods/exec`, `pods/attach` and `pods/ephemeralcontainers`; there is no second layer inside this brief, because the in-pod socket session is how CNPG's own tooling administers the instance, and the doc says so. Cell-to-cell isolation is the database layer's, as in brief 26; the credential layer is stated, not claimed. <!-- graph: encoded desk-containers/26→desk-containers/27 -->
