- **Image.** `postgres:18.6-trixie`, pinned by digest (`postgres:18.6-trixie@sha256:<digest>`). Re-establish the digest at implementation time from the registry, not from this brief. 18.6 is the CloudNativePG 1.30.1 default operand's PostgreSQL version, so brief 27's migration is same-major and same-minor. PostgreSQL 19 is beta only and is not used. Changing the major version of an existing volume in place is not supported by PostgreSQL: the doc says a major upgrade is dump, new volume, restore. The compose file refuses to start with an unpinned tag (Verify row 2).
- **Volume.** A named volume `assay-postgres-data` mounted at `/var/lib/postgresql`. The PostgreSQL 18 image moved its `VOLUME` there from `/var/lib/postgresql/data`, and its `PGDATA` is `/var/lib/postgresql/18/docker`. Mounting the old path leaves the data in an anonymous volume. Never place this volume on a network filesystem (doc 14 line 15).
- **Network exposure.** The port is published on `127.0.0.1` only, as `127.0.0.1:${ASSAY_PG_HOST_PORT:-5432}:5432`. No TLS in the local profile; the listener is loopback-only, and the doc says so. Remote cells use brief 27's cluster, which has TLS.
- **Health check.** `pg_isready -U postgres -d postgres` with a start period, interval and retries. `docker compose up --wait` returns only once the server is healthy.
- **Superuser password.** Arrives at runtime as a compose secret per `containers/secrets.md` §4.2, `secrets: pg_superuser: file: ${ASSAY_PG_SECRETS_DIR:?set ASSAY_PG_SECRETS_DIR}/superuser.password`, read through `POSTGRES_PASSWORD_FILE`, which points at `/run/secrets/pg_superuser`. `${VAR:?}` makes compose refuse to start when the directory is unset; there is no default path inside the repository. The doc suggests `~/.config/assay/postgres/` with directory mode 0700 and file mode 0600. No password, real or example, is committed. No image is built here, so §6's layer rule is met trivially.
- **Per-cell names.** Cell names may contain `-` and `/` (cells are paths under the cells root). The database and role name is `cell_` plus the cell name lowercased, with each `-`, `/` and `.` replaced by `_`. Example: `example-cell` maps to `cell_example_cell`. `provision-cell.sh` refuses a cell name outside `^[A-Za-z0-9][A-Za-z0-9._/-]*$` and a mapped name longer than 63 bytes (PostgreSQL's identifier limit). Two cell names can map to one identifier, for example `a-b` and `a/b`. To catch that, the script stores the original cell name with `COMMENT ON DATABASE`, and it refuses when an existing database's comment names a different cell.
- **Per-cell role.** `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS`, with `CONNECTION LIMIT` set from a script flag (default 20). The role owns its database, so graph-execution/19 and /26 can create their own schemas in it without any other privilege.
- **Per-cell isolation at the database layer.** `REVOKE CONNECT, TEMPORARY ON DATABASE <db> FROM PUBLIC`, so only the owner (and the trusted administrator) connects. `00-harden.sql` does the same on `postgres` and `template1`. Object ownership is the second layer: a role that did connect to another cell's database still owns nothing there and is granted nothing. This profile isolates cell roles from each other, not from the database administrator; and on a shared OS user a host cell can become that administrator (next fact). The administrator is trusted (doc 11 §"State has explicit homes", currently line 233; doc 14 line 13), and a profile that needs more gets a separate server.
- **The credential layer does NOT isolate host cells from each other, and the brief says so rather than claiming it.** Every consumer of this profile is a host cell (the check rows below refuse `container` cells). Host cells run as the operator's OS user, with that user's file authority, and `docs/cellctl.md` §"External launcher compatibility" states that the launch contract does not establish isolation from another unrestricted host process. Every cell's pgpass file is a 0600 file owned by that same user, and so is the backup directory. Any host cell's process can therefore read another cell's pgpass file and connect as that cell; `REVOKE CONNECT` never comes into play. Mode 0600 guards against other OS users only. Worse, any host cell can act as the database superuser, by either of two paths. First, the superuser password file under `ASSAY_PG_SECRETS_DIR` belongs to the same OS user, and the port is published on loopback, so a cell can read the file and connect as `postgres`. Second, any process that can reach the Docker daemon gets an in-container superuser session through `docker compose exec`, which is the path `provision-cell.sh` itself uses. So on the shared-OS-user profile the boundary does NOT hold against a same-user cell at all: such a cell can become the administrator this profile trusts, and every control in this brief that guards against a cell (the restore role, `NOLOGIN`, `REVOKE CONNECT`) is moot for it. Doc 11 §"State has explicit homes" (currently line 233) asks for separate "secrets access" per cell; this profile does not provide it on a shared OS user. So the isolation this brief claims, tests and documents is the database layer's: one cell's role, used as that role, cannot open another cell's database or act outside its own. `docs/postgres.md` (planned) states the boundary in those words, states both superuser paths, and says that separating cells needs a mechanism this brief does not ship. That mechanism must withhold, from every cell, other cells' credential and backup paths AND the superuser secret directory AND Docker daemon access (no membership in the `docker` group, no reach to the daemon socket, no rootless daemon under the cell's user). Candidates: a separate OS user per cell that meets all three, a harness sandbox that denies all three, or a separate server per cell. A per-cell OS user in the `docker` group, or a sandbox that still allows the secret directory or the socket, does not qualify, and the doc says so. The `cellctl check` rows and the drill never word a passing result as "cells are isolated".
- **Provisioning is idempotent and runs on a live server.** `/docker-entrypoint-initdb.d` runs only when the data directory is empty, so it holds only `00-harden.sql`. Cells are added at any time with `provision-cell.sh --cell <name> --passfile <path>`. The script runs `psql` inside the container through `docker compose exec -T`, with SQL on stdin.
- **The plaintext role password never reaches the server.** PostgreSQL's `CREATE ROLE` documentation warns that an unencrypted password "is transmitted to the server in cleartext, and it might also be logged" in the server log; with the default `log_min_error_statement = error`, a failing statement is logged in full, and the server log is the container log. So `provision-cell.sh` reads the password from the pgpass file, computes a SCRAM-SHA-256 verifier on the client (the `SCRAM-SHA-256$<iterations>:<salt>$<StoredKey>:<ServerKey>` form PostgreSQL stores, which is what psql's `\password` sends), and sends only that verifier on stdin as the `PASSWORD` of `CREATE ROLE` / `ALTER ROLE`. Which client-side tool computes it (for example Python's `hashlib.pbkdf2_hmac`) is re-established at implementation and recorded in the PR body; the script refuses rather than fall back to sending plaintext. Second layer, independent of the first: the provisioning session first runs `SET log_min_error_statement = panic` and `SET log_statement = none`, so even a statement that does fail is not written out. The compose file does not preload `pg_stat_statements`, whose view would otherwise keep the `CREATE ROLE` text, verifier included; the provisioning and restore sessions also run `SET pg_stat_statements.track_utility = off`, so an adopter who adds it later keeps the property, and the doc says why. The password is never on any argv and never in an environment variable.
- **Per-cell credential file.** One file per cell in libpq pgpass format, `host:port:database:user:password`. The operator creates it, or `provision-cell.sh --generate` writes it at mode 0600 with 32 random bytes, base64url-encoded. The script refuses a file whose mode is not 0600 or 0400, and a password outside `[A-Za-z0-9_-]{32,}`; that set has no character pgpass or psql quoting treats specially. The file lives outside the repository, beside the cell's other hand-provisioned credentials, by the same rule as `DESKD_GITLAB_TOKEN_FILE`. Its mode guards against other OS users, not against other cells (see the credential-layer fact above).
- **How a cell finds its database: two `cell.env` keys and no new cellctl verb.** `CELL_DB_DSN` is a libpq connection string with no password, for example `host=127.0.0.1 port=5432 dbname=cell_example_cell user=cell_example_cell sslmode=disable`. `CELL_DB_PASSFILE` is the absolute path of the cell's pgpass file. Both are registered in `envkeys.go` as `envCell` levers, so `cellctl set` accepts them and `TestEnvKeyRegistryIsComplete` covers them. When `CELL_DB_DSN` is set, every role window gets `ASSAY_CELL_DB_DSN=<dsn>` and `PGPASSFILE=<path>`. libpq reads `PGPASSFILE` itself, so the password never appears in an environment variable or on a command line. When the key is unset, both variables are absent: a cell with no database is unchanged. That follows the `repairAdmissionValue` precedent in `launch.go`. The composition goes in four places: host launch (`launch.go`), the dry-run plan (`desk.go`, one `[dry-run] env` line each), the scrubbed allowlist (`env.go` — append both to `scrubbedEnvKeys` and add `scrubbedEnvValue` arms that return "" when unset), and `codex_environment.go`'s forwarded key list. The parity fixtures set neither key, and an empty value is skipped. The shell-oracle parity diff must therefore stay clean with no oracle edit (Verify row 9).
- **`cellctl check` rows**, active only when `CELL_DB_DSN` is set; otherwise one `n/a` line:
  - the DSN has no `password=` keyword and no password in URL userinfo;
  - `CELL_DB_PASSFILE` is set, absolute and readable, and has mode 0600 or 0400. Use the same mode helper and Windows behaviour as the existing 0600 checks;
  - on a `container` kind cell, the check FAILS with a message saying container cells cannot reach the database yet. Container cells (`cell-containers-v1`) refuse any environment or mount beyond their plan and run on a dedicated network, so wiring them needs a schema change. That is out of scope here; the failure names it so it is never silently missing.
- **Backups: per-cell logical dumps.** `backup.sh --out <dir>` writes, for every `cell_%` database, `pg_dump -Fc` to `<dir>/<UTC stamp>/<db>.dump`. It also writes `pg_dumpall --globals-only --no-role-passwords` to `globals.sql`, plus a `manifest` holding each file's sha256, the server version and the dump start time. It runs under `umask 077`, so each stamp directory is 0700 and each file 0600, and it refuses an `--out` path inside the repository working tree. Retention: keep the newest N stamps (default 7, `--keep`). Scheduling is the operator's (cron, launchd or a systemd timer); the doc gives one example each and suggests daily.
- **Stated recovery point.** A restore returns a cell to the start of the dump it restores. The recovery point objective equals the dump interval, 24 hours with the suggested daily schedule. This profile has no point-in-time recovery; WAL archiving is brief 27's job. The doc states this plainly and claims no zero loss (doc 14 line 44). Each cell restores alone, without touching the other cells.
- **Restore leaves the cell unable to connect.** `restore.sh --cell <name> --dump <file>` sets the cell's role `NOLOGIN` before anything else, then refuses if any session for the role is still open (`pg_stat_activity`); the operator stops the cell with `cellctl down <cell>` first. It then renames the current database aside (never drops it), creates a fresh database with the same owner and the same `REVOKE ... FROM PUBLIC`, and restores into it as described next. The role stays `NOLOGIN` afterwards. The cell cannot write until the operator runs `provision-cell.sh --cell <name> --enable-login`. The doc places that step after the consumer's reconcile procedure (graph-execution/16's operator incarnation; doc 14 lines 46 and 56). This is the local layer that makes the procedure unavoidable. The consumer's own check that a mismatched activation record starts paused is the second, independent layer, owned by graph-execution/19.
- **A restore never runs cell-controlled code as the superuser.** A dump of a cell database is cell-controlled input: the cell role owns its database, so it can define a `SECURITY INVOKER` function and a table whose `CHECK` constraint or generated column calls it. The restore's data load then calls that function for every row, as whoever the restoring session is. If that were the superuser, the function could give its own role `SUPERUSER` or read every other cell. `SET ROLE` or `pg_restore --role` from a superuser session is not enough on its own: an invoker function can run `RESET ROLE` and is back to the session's authenticated user. So the session that loads the data authenticates as a non-superuser:
  - `restore.sh` creates a one-shot role `assay_restore`: `LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS NOINHERIT`, `CONNECTION LIMIT 1`, `VALID UNTIL` the restore's deadline (a script flag, default one hour), with a one-shot random password set through the client-computed verifier above. Its only membership is the one cell role being restored, granted `WITH INHERIT FALSE, SET TRUE`: `SET ROLE` (which `pg_restore --role` uses) needs only the membership, and a non-inheriting member gets none of the cell role's rights while it is itself. Because of that, it is granted `CONNECT` on the one fresh database explicitly. It refuses if `assay_restore` already exists, which also stops two restores running at once.
  - The data load runs as `pg_restore --role=<cell role> --no-owner --exit-on-error --single-transaction`, connected as `assay_restore`. Objects end up owned by the cell role. A `RESET ROLE` inside cell code lands on `assay_restore`, which holds only `CONNECT` on that database and no inherited rights.
  - Extensions are the one superuser step. `restore.sh` lists the dump's `EXTENSION` entries (`pg_restore -l`) and takes only each entry's name. For each, it runs a fixed `CREATE EXTENSION <quoted name>` built from that name, as the superuser, in the fresh database before the data load (the extension's scripts ship with the image, not with the dump), and leaves the entries out of the data load's restore list (`-L`). It never replays the dump entry's SQL as the superuser: a tampered archive's entry text is arbitrary SQL. It refuses an extension the image does not provide, one that is neither marked trusted in the image nor on the operator's `--allow-extension` list (a cell owner could only have created trusted ones itself), and one it cannot create before the cell's own objects exist.
  - Teardown is a trap on every exit path, and cell code may have tried to make the role outlive the restore: the data load commits the cell's own `CHECK`-constraint code, which, acting as the cell role, can `GRANT` on its tables to `assay_restore`, and after `RESET ROLE` can create an object `assay_restore` owns or set its password. The trap therefore runs, as the superuser, in this order: (1) `ALTER ROLE assay_restore NOLOGIN`; (2) `pg_terminate_backend` for any session of that role; (3) in the restored database, `REASSIGN OWNED BY assay_restore TO <cell role>` then `DROP OWNED BY assay_restore` (which also revokes its grants, the database `CONNECT` included); (4) `DROP ROLE assay_restore`. Step 1 comes first so that a failure in any later step still leaves no login. Each step that fails exits non-zero naming the step (for example `teardown step 4: DROP ROLE assay_restore failed`), and the restore reports failure even if the data load succeeded. `VALID UNTIL` is the independent second layer: a role that survives a failed teardown cannot log in past the deadline whatever password the cell set. `check-isolation.sh` fails if the role exists outside a running restore.
  - How `assay_restore` reaches the server (the container's local socket, with its one-shot password in a 0600 file inside a `mktemp -d` directory the trap removes) is re-established against the image at implementation and recorded in the PR body. It is never an argv or environment value, and the script refuses rather than fall back to a superuser session.
- **Aside names.** The database a restore renames aside is named `aside_<YYYYMMDDTHHMMSSZ>_<h>`, where `<h>` is the first 8 hex digits of the sha256 of the cell database's name: 31 bytes, under PostgreSQL's 63-byte identifier limit for every cell name, so it is never silently truncated. `COMMENT ON DATABASE` records the cell name and the original database name. It does not match `cell_%`, so `backup.sh` does not dump aside copies and nothing treats one as a cell; the doc says so, and an operator who wants an aside copy kept dumps it by hand. The rename keeps the database's `REVOKE ... FROM PUBLIC`, and `check-isolation.sh` checks `aside_%` databases for a `PUBLIC` `CONNECT` grant as well as `cell_%`. If two restores of one cell fall in the same second, the second rename fails and the restore stops before changing anything.
- **The drill** is `drill.sh`. It brings up a throwaway compose project with a unique project name, a fresh volume and a free host port. It provisions two cells and proves database-layer isolation and attributes, then writes rows, backs up, and restores into a second throwaway server. It compares the dump against a dump of the restored database, with each side's data-only text sorted, and requires them equal. It plants the escalation and persistence probe described in Verify row 7 in one cell before the backup, and after the restore proves no role gained `SUPERUSER`, `assay_restore` is gone, and the probe's password does not log in. It forces one provisioning run to fail at the role statement and proves the container log holds neither that cell's password nor its verifier. It proves the restored role is `NOLOGIN` until `--enable-login`, then tears everything down, including on failure (trap). It never touches the operator's `assay-postgres` project or volume.
- Not a core-system brief, but its credential custody is human-gated (see `gate-why`). At the database layer, the single control between one cell's role and another cell's database is `REVOKE CONNECT ... FROM PUBLIC`; object ownership is the second layer, and `check-isolation.sh` detects drift in the first. Between host cells on one OS user, nothing in this brief separates credentials, and any such cell can reach the superuser through the secret file or the Docker daemon; that boundary is stated, not claimed (the credential-layer fact above), and the remedies that would close it are named, not shipped. Between a restored dump and the superuser, the single control is that the data load's session authenticates as `assay_restore`; the second layer is that `assay_restore` is a non-inheriting member of the one cell role only, so cell code that escapes the `SET ROLE` holds nothing at all. Between cell code and a surviving restore login, the single control is the trap's ordered teardown; `VALID UNTIL` is the second layer.
