layering: the pure library `statusgen/evaluation` owns the v2 schema, digest computation and the v1/v2 judgment, reading git only through its `Repo` port. The statusgen adapter supplies one batched, memoized listing per revision. Cross-module consumers read the result through `statusgen --coverage --json` or `statusgen witnessdigest --json`, never by importing statusgen or re-parsing cells. No new module, service or daemon.

trust-assumption: v2 detects staleness, not forgery. The writer computes every digest and self-reports `runner_class`, `network`, `tools` and the outcome, so anyone who can write a record the reader parses can write one it accepts. A record's authenticity rests on the same controls as a v1 cell today: who authored the Evidence change (`evidenceactor.go`, tamper-evident, not tamper-proof), review of the Evidence change request, and the change request's verified landing (judgment step 2). v2 therefore must not weaken any v1 identity, acceptance-text or dirty-tree check, and binds the executing identity, the acceptance text and the outcome inside the record id so that a record cannot be replayed onto another row or outcome.

single-point-of-failure: the author's `inputs:` declaration, checked only by human review of the brief, is the one control against an under-declared source file: a file the row reads but the declaration omits is not hashed, so a change to it cannot refuse the witness. Behind it for that fault: NONE in this split. The other layers cover different faults and do not catch this one: implicit inputs cover module and lock files, attributes and tool pins; the whole-tree digest applies only when `inputs:` is absent or unparseable; the environment rule covers network, forge and cluster rows. The mechanical lower bound below (every path the Command cell names literally must be declared) catches only the omission of a path the command itself names, not of a file it reads transitively. A second layer for transitive reads is not feasible in this brief: a shell command's read set cannot be derived statically (the #2304 command parser could not read 76 rows), and the alternative, recording the files a row actually opened, needs the network-less container runner that statusgen/37 builds plus a file-access tracer on every supported host. That observed-read check is the named follow-up. Until it exists, Human decision option 2 keeps host and back-filled runs from releasing, which narrows who can produce a releasable record but does not detect under-declaration.

## Human decision

A v2 witness records a digest of the files a Verify row read and the change request that delivered it. Coverage releases the row when every recorded digest still equals the content at the item's revision. A digest cannot capture a row that depends on the network, a code-hosting service or a cluster, so those rows are never released by digest and are reported as needing a re-run. The open question is which runs count as environment-free.

Options:
1. Recommended: a run counts as environment-free when it ran in the pinned, network-less container runner, or when it ran on a host (or was back-filled) and its row is neither marked environment-dependent by its author nor names a network tool in a form the library can read. A host row whose command cannot be read is reported as needing a re-run.
2. Strictest: only runs in the pinned, network-less container runner count. Host runs and back-filled records are recorded for audit but always reported as needing a re-run.
3. Widest (not recommended): any run not marked environment-dependent by its author counts, including commands the library cannot read.
4. Option 2, and in addition declared scope does not release yet: a v2 record releases only at whole-tree scope until the observed-read check exists. `inputs:` is still parsed, linted and recorded, but narrowing a row's scope then needs a later ruling rather than this brief's merge.

Default if no answer: option 2 after 2026-11-03.

Option 2 is the strictest environment choice, so no wider release is inferred while the question is open. Under options 1 to 3, merging this brief approves the scope narrowing that each brief's `inputs:` declares, checked by human review of that brief; option 4 withholds that approval, at the cost of keeping refused every stuck brief whose cause is whole-tree scope.

## Interface contract

**Schema marker.** A v2 Runner cell is `<runner> @ [w2] cr:<id> rec:<record-id>`, followed by the same on-behalf-of and runner-source parentheticals a v1 cell carries. `<runner>` is the executing identity exactly as verifyrun writes it in a v1 cell today, so every identity read (`implementerAttributed`, `evidenceHasIndependentRow`, the verifier floor, `runnerKey`) keeps working unchanged. The runner class is recorded in the record, never in place of the identity. `<record-id>` is the full 64-hex id; there is no prefix resolution. The bracketed marker is not a valid git object name or ref, so a reader that predates v2 lifts `[w2]`, fails to resolve it, and refuses (the version-skew rule). A cell with any other `[w<N>]` marker is an unknown schema. A cell with no bracketed marker is v1.

**Witness record (v2).** One JSON file per run at `docs/streams/witnesses/<stream>/<NN>/<record-id>.json`, keys sorted, written by statusgen/37 and parsed here. Every field below is inside the record id:

- `schema: 2`, `brief` (the brief id), `row` (the Verify row id),
- `command_sha256`, `expect_sha256`, `class_sha256` (SHA-256 of the Verify row's Command, Expect and Class cell text at the revision the run read; the Command text is first normalised by `NormalizeCommandText`, the normaliser v1's Command check uses, so step 3 and step 5 compare it the way v1 does),
- `runner` and `runner_source` (the executing identity and its source, as written in the cell),
- `runner_class` (for example `host`, `harness-container`, `k8s-pod`), `network` (`none` or `available`), `tools` (statusgen and desk-tools release, Go version, harness image digest when containerised) and `tools_source` (`observed`, `inferred-from-pins`, or `none` when the tools are unknown),
- `origin` (`run`, or `backfill` for a record derived by statusgen/38); a back-filled record also carries `source_cr` (the merged change request whose commit list held the witnessed commit) and `source_cell` (the v1 cell text),
- `result` (the Result cell, which carries the exit status), `exit`, `output_sha256` (the output digest cell) and `date`,
- `cr` (the forge's change-request id that delivers this record, or `pending`),
- `scope` (`declared` or `whole-tree`),
- `inputs` (repo-relative, slash-separated path → git blob id; a required path missing at the revision read is written `absent`, which step 9 refuses, so no record of a missing input ever releases),
- `implicit` (the same shape, for implicit inputs), `attributes` (path → SHA-256 of the resolved attribute set), and `tree_digest` for whole-tree scope: the SHA-256 of the sorted `<mode> <blob id> <path>` lines for every non-bookkeeping file in the tree read (`git ls-tree -r` at a revision; tracked and untracked, non-ignored files in a working tree),
- `dirty_paths` (every non-bookkeeping path that was modified, deleted or untracked in the working tree when the row ran; empty for a clean tree),
- `informational` (`commit`, `dirty`); never read by the judgment, though inside the id. `commit` is the full object id of the commit the run read: 40 or 64 lowercase hex characters, never abbreviated.

`record-id` is the SHA-256 of the canonical record. Because `cr` is inside it, binding a `pending` record to its change request writes a new record and a new id (statusgen/37's `--bind-cr`, allowed only before the record reaches the default branch). The reader recomputes the id and refuses on mismatch.

**Digest.** A git blob id of the normalised content: for a committed revision, the id from `git ls-tree -r`; for a working tree, `git hash-object --stdin-paths` (which applies the repository's clean filters and end-of-line attributes). CRLF checkouts and Windows path separators therefore produce the same digest. Paths are repo-relative and slash-separated. In a working tree a symlink's digest is the blob id of its link text, the id `git add` would store, never of its target, so committed and working-tree digests agree. Because that id does not change when the link's target changes, a required path that is a symlink (mode `120000`) is refused on both sides: the writer records no passing witness and the reader refuses (`witness-input-symlink: <path>`, step 9). An author declares the target instead. At whole-tree scope the link text and an in-repo target are both inside the tree digest; an out-of-repo target is outside every digest, like any other read from outside the repository (single-point-of-failure).

**Declared inputs.** A new `## Context` field `inputs:` lists the files and directories the Verify rows read, in the `files:` grammar of `docs/declared-input-scope.md`, reimplemented in `statusgen/evaluation` against the same fixtures. Paths under `docs/streams/**` and `STATUS.md` stay bookkeeping exactly as today and are a lint PROBLEM inside `inputs:`. An absent or unparseable `inputs:` means scope `whole-tree`. At declared scope the required set at a revision is: each declared file path, whether or not it exists there; every file that exists there under each declared directory, bookkeeping paths excluded; and the implicit inputs below. Under Human decision option 4 a `scope: declared` record is `witness-rerun-owed` whatever its digests, and statusgen/37's writer records whole-tree scope for every run.

**Literal-path lower bound.** Every repo-relative path that a Verify row's Command cell names literally and that the library can read (a `cd` target, a package path such as `./evaluation/`, a file argument) must lie inside the declared set. `--lint` reports a violation as a PROBLEM, and the reader refuses with `witness-input-undeclared`. This is a partial check: it catches an omitted path the command names, not a file the command reads transitively (see single-point-of-failure).

**Implicit inputs**, derived by the library, never declared. The module and lock files are those that exist at the revision read (the working tree for the writer, R for the reader); a candidate name that does not exist there is not in the set: for every input path, each `go.mod`, `go.sum`, `go.work`, `go.work.sum`, `package.json`, `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `Cargo.toml`, `Cargo.lock`, `pyproject.toml`, `uv.lock`, `poetry.lock` and `requirements*.txt` on the path from that input to the root; the resolved git attributes of each input (`git check-attr -a --source=<rev>`); `plugins/assay/paired-versions.yaml` (the tool and harness pins); and every `policy` or `build` path in the brief's WI-2 dependency manifest that applies to the row. The pin file and the WI-2 paths are required whether or not they exist, like a declared file, so a missing one is `witness-input-absent`. Because the module and lock files enter the set only where they exist, one removed after recording is `witness-input-set-changed` and one added after recording is `witness-input-undeclared-at-record` (step 7).

**Judgment of a v2 claim at revision R** (all must hold, else the named gap; the first step that fails, in the order below, names it, so under option 2 or 4 a host or back-filled record reports step 6's `witness-rerun-owed` before any input comparison):
1. The record exists, parses, and its id matches the cell (`witness-record-missing`, `witness-record-mismatch`).
2. `cr` is set, not `pending`, equal in the cell and the record, and verified: the first-parent commit on R's history that added the record names that change request in a recognised landing form, and its diff also changes the citing brief (`witness-cr-unbound`, `witness-cr-mismatch`, `witness-cr-unverified`). The recognised landing forms are one table in the library: the GitHub merge-commit subject, the GitHub squash subject suffix, and the GitLab merge-commit trailer. Each form also fixes the commit's shape. The two merge-commit forms need exactly two parents, with the record present at the second parent and absent at the first; the squash form needs exactly one parent. A commit whose text matches a form but whose shape does not is `witness-cr-unverified`. Every form remains a textual proof wherever the forge can put a branch's own commit on the default branch's first-parent history. Offline, a rebase-landed single-parent commit whose subject ends `(#N)` cannot be told apart from a squash of change request N; and under GitLab's fast-forward or semi-linear merge method, a branch's own two-parent commit carrying another merge request's `See merge request` trailer passes both the shape check and the text check. Such a commit still reached the default branch through some merged change, so the residual risk is a misattributed change request, not an unreviewed landing. Only `--forge` closes it, by confirming that change request N's landed commit is the adding commit. A landing in no recognised form (a fast-forward or rebase merge, for example) is `witness-cr-unverified` offline; with `--forge`, the forge seam may confirm that the change request is merged and that its landed commit is the adding commit. The offline proof that the change request merged is that the adding commit lies on the default branch's first-parent history and is an ancestor of R. The default branch is `refs/remotes/origin/HEAD`; else, with `--forge`, the branch the forge reports as default; else `refs/remotes/origin/main`, else the local `main`. A `witness-cr-unverified` caused by no default branch resolving says so and names the remedy (`git remote set-head origin --auto`), so a repository whose default branch has another name and no `origin/HEAD` gets a one-command fix rather than a silent refusal of every offline claim. When none resolves, or the adding commit is on R's first-parent history but not on the default branch's (a feature branch whose own commit carries a merge-style subject), the offline judgment is `witness-cr-unverified`; only `--forge` can then confirm the merge. This ancestry read concerns the record's landing, not the witnessed commit.
3. The record's `brief` and `row` equal the citing brief and Verify row, and the citing witness row's Result, output-digest and Date cells equal the record's `result`, `output_sha256` and `date` (`witness-record-replayed`). The SHA-256 of the citing witness row's Command cell, normalised as in `command_sha256`, equals the record's `command_sha256` (`witness-command-cell-mismatch`). This is the v2 form of v1's Command check (L348–350), which compares the citing Evidence row's Command cell with the Verify row's: step 3 ties that cell to the record, and step 5 ties the record to the current Verify row, so a v2 cell that passes both has an Evidence Command cell equal to the current Command. A record whose `command_sha256` matches the current Verify row but not its own Evidence Command cell (for example a hand-landed row whose verifier ran an adapted command and recorded that command in the cell) is refused here, as v1 refuses it.
4. The record's `runner` equals the cell's identity token (`witness-runner-mismatch`).
5. `command_sha256`, `expect_sha256` and `class_sha256` equal the current Command, Expect and Class cells (`witness-command-changed`, `witness-expect-changed`, `witness-class-changed`). This keeps v1's Expect-changed refusal: a loosened Expect never releases an old pass.
6. The environment rule per Human decision (`witness-rerun-owed`); a row whose Class carries `+env` is always `witness-rerun-owed`.
7. The recorded `inputs` and `implicit` keys equal the required set at R (declared plus implicit, or whole-tree) as sets, and the `attributes` keys equal the recorded input paths. A required path with no recorded key is `witness-input-undeclared-at-record: <first path>`; a recorded key that is no longer required (a file deleted under a declared directory, a removed `go.sum` or `go.work`) is `witness-input-set-changed: <first path>`. A subset test is not enough, because a key that leaves the required set would otherwise never be compared. At whole-tree scope the required `inputs` and `attributes` sets are empty and the required `implicit` set is the pin file plus the WI-2 `policy` and `build` paths, compared by blob id even though the tree digest covers them, so a dependency under a bookkeeping path is not lost; any other recorded key is `witness-input-set-changed`, and the tree digest stands for every other file, `.gitattributes` files included. The literal-path lower bound also holds (`witness-input-undeclared`).

**Recorded outcome.** Steps 1–5 apply to a v2 cell whatever its Result, so a changed Command, Expect or Class is reported by step 5 for every outcome, and an Evidence Command cell that differs from its record by step 3. This is intended: a recorded failure whose record is missing, mismatched, replayed or not yet bound (`pending`, or a landing step 2 cannot verify, including an Evidence change request that has not merged) reports that step's gap, which is `could-not-check` or, for steps 3 and 5, `error`, not `fail`. v1 reports `fail` whatever the binding, so for such a cell the leading reason on the board (`coverageResultOrder`, `statusgen/coverage.go` L83, ranks `fail` first) becomes the binding gap. The claim is held either way, and `checkWitnesses` still reports the recorded failure; a failure is reported as a v2 outcome only once its record is bound to the row it cites. After step 5, a cell that does not record a pass reports its outcome and stops: a recorded failure is `fail` with `witness-outcome-fail`, a recorded could-not-run is `could-not-check` with `witness-outcome-could-not-run`, and a Result that parses to no known state is `error` with `witness-outcome-unparseable`. A recorded pass on a row now flagged prose-led is `could-not-check` with `witness-prose-led: <the row's prose-led note>`, as v1's demotion (L359–361) is. Steps 6–10 apply only to a recorded pass on a row that is not prose-led. These are the v2 forms of v1's `StateFail`, `StateCouldNotRun` and unparseable-Result branches (L434–442) and of its prose-led demotion, which a v2 cell never reaches.

**The v2 comparison is its own function, dispatched before any v1 code reads a revision.** On main (`statusgen/evaluation/coverage.go` at b267d1120), a passing witness is judged in `resolveVerifyClaim` (L339). Its `classifyRevisionDetail` call (L362) relates the witnessed commit to the item's revision, through `witnessTreeApplies` for a scope that includes every `source` dependency. After a match it reads the row's Expect at the witness's base commit (L385–405), and its WI-2 loop compares each `policy`, `build` or `environment` dependency through `depFingerprintSame` at that base (L410–423). Each of those reads needs the witnessed commit, so a v2 claim reaching any of them would be could-not-check whenever that commit was squash-orphaned. v2 therefore adds `judgeWitnessV2` in `witness.go`. `resolveVerifyClaim` dispatches to it on the parsed cell schema right after it selects the latest witness (L347) and before the Command check (L348–350), so the dispatch also precedes the state switch, the prose-led demotion (L359–361) and the `classifyRevisionDetail` call at L362; an unknown schema returns its named gap at the same point. None of v1's checks from L348 on runs for a v2 or unknown-schema cell. The Command check, the `StateFail`, `StateCouldNotRun` and unparseable-Result branches and the prose-led demotion each have a v2 form inside `judgeWitnessV2` (steps 3 and 5 and Recorded outcome above), so a v2 claim's every reason carries a v2 gap name. The Command check's v2 form is the pair of step 3 (Evidence Command cell against the record) and step 5 (record against the current Verify row); step 5 alone compares a different pair and would not refuse a cell whose Evidence Command differs from the Verify row. `checkWitnesses` (`statusgen/verifyrun.go` L1529) and the witness gate's `latestFailFirst` (`statusgen/witnessgate.go` L327) compare the Evidence Command cell with the Verify row for every cell, v2 included, and stay unchanged; with steps 3 and 5, coverage refuses every v2 cell they refuse on that comparison, so the board, `--coverage --json` and auto-flip never release a row those two refuse. Coverage can refuse more (a record that matches neither its Evidence cell nor the Verify row while those two agree), which holds the claim. The empty-witness case before the dispatch (L340–342) is unchanged, because it has no cell to dispatch on. A v1 cell reaches L348 exactly as today. `judgeWitnessV2` returns `resolveVerifyClaim`'s own `(result, reason, revision)` triple, so `evaluateCoverage` (`coverage_api.go` L221), the board, `--coverage --json` and auto-flip read v2 verdicts unchanged. For a v2 claim:
- `revision` is the record's `informational.commit`, the commit the run read, so the receipt keeps the revision the row ran at. It is not the cell's token after `@`, which for a v2 cell is `[w2]`. It is empty when the record cannot be read (step 1), when the schema is unknown, and when `informational.commit` is not a full object id (exactly 40 or 64 lowercase hex characters), so a writer-supplied string of any other form never reaches `Claim.Revision` or `--coverage --json`. It is informational and never read by the judgment, so a malformed value empties the revision without changing the result.
- Step 5's `expect_sha256` comparison replaces v1's Expect read at the witness's base. When the caller supplies an acceptance revision (`CoverageInput.AcceptanceRevision`, or a per-row approved amendment), the row's Expect read at that revision must also equal the current Expect, exactly as v1 checks it (L386–392, L400–405). That revision is a protected, immutable definition, not the witnessed commit or a base of it, so a squash merge does not remove it; an unreadable one is could-not-check.
- The brief's WI-2 dependencies are judged inside `judgeWitnessV2`, not in the L410 loop. A `policy` or `build` path is an implicit input compared by blob id at R. An `environment` dependency compares the caller-supplied `Recorded` and `Current` fingerprints (`coverage_api.go` L138–146) by the rule `depFingerprintSame` applies today (L902–906), with no revision involved: either value empty is could-not-check, and unequal values are `witness-environment-changed: <name>`. The record does not carry environment fingerprints, so, as for v1, this check is live only where a caller supplies a manifest (none does today; see Context).

It reads no object at the witnessed commit or at any base, and never calls `classifyRevisionDetail`, `witnessTreeApplies` or `depFingerprintSame`.

The v1 path, from L348 on, is unchanged (row 6). The witnessed commit, its ancestry and the landed-twin search are not consulted for v2 (step 2's ancestry read is of the record's landing commit). Steps 1–8, step 9's `absent` and symlink checks and step 10 are gates in front of the comparison inside `judgeWitnessV2`, not a second judge. **Results and unreadable states.** Every v2 outcome is one of `resolveVerifyClaim`'s results, and its reason starts with the gap name; only a release is `pass`. `witness-input-changed`, `witness-input-set-changed`, `witness-input-undeclared-at-record`, `witness-environment-changed` and `witness-tool-changed` are `wrong-revision`, as a changed WI-2 dependency is today: the claim is held until it is re-run, and the receipt keeps its revision. `witness-command-cell-mismatch`, `witness-command-changed`, `witness-expect-changed` and `witness-class-changed` are `error`, as v1's acceptance-definition guard (including its Command check at L348) is, and so is `witness-outcome-unparseable`. `witness-outcome-fail` is `fail`. Every other gap is `could-not-check`. This holds for a changed Command too: the dispatch precedes v1's Command check, so a consistent record whose Command digest matches its own Evidence Command cell, cited by a Verify row whose Command changed after the run, reports `witness-command-changed`, never v1's command reason; an inconsistent record, whose `command_sha256` matches the current Verify row but not its own Evidence Command cell, reports `witness-command-cell-mismatch` at step 3. An unreadable state is `could-not-check` with `witness-unestablished: <what>`, never a match: a `Repo` port error inside `judgeWitnessV2` or step 2 (`ListTree`, `CheckAttr`, the first-parent log, an ancestry read); a landing commit whose parent is missing from the object store, as in a shallow or partial clone (`witness-unestablished: shallow`); and an acceptance revision that cannot be read. Every v2 git read runs with replace objects disabled (`GIT_NO_REPLACE_OBJECTS=1`), so a replace ref cannot give a landing commit a parent shape or an ancestry it does not have, and a landing commit at a shallow boundary is never judged by its grafted parents.

**Seams.** `statusgen --coverage --json` gains, per claim, `witness: {schema: 1|2, judgment, gap, cr, runner, independent, evidence_actor}` with a top-level `witness_schema_version: 1`. `runner` is the cell's identity token; `independent` is the verdict of the existing offline identity reads for that row (the independent-row read and the verifier floor); `evidence_actor` is the existing Evidence-actor classification of the commit that authored the citing Evidence line (`verifier`, `other` or `unknown`). These are reported from the reads statusgen already has, so no consumer parses a Runner cell or runs `git blame` itself. For a v1 claim the field also carries `landing_cr`: the change request named, per step 2's landing-form table, by the first-parent commit that landed the citing Evidence line (empty when the landing is in no recognised form). `statusgen witnessdigest --json --brief <path> [--rev <rev> | --worktree] [--row <id>]` prints the canonical v2 content fields (`inputs`, `implicit`, `attributes`, `tree_digest`, and `dirty_paths` with `--worktree`) and, with `--row`, that Verify row's `command_sha256` (of the normalised Command text), `expect_sha256` and `class_sha256` at the same revision, computed by the library; it never prints a releasable record. Cross-module consumers use only these.

**Performance budget.** One `git ls-tree -r`, one `git check-attr --stdin` and one `git log --first-parent --diff-filter=A` over `docs/streams/witnesses/` per distinct revision per run (the default-branch tip counts as one more revision), memoized in the existing `memoRepo`; no per-row git process. The offline `statusgen --root . --coverage` over the corpus stays within 1.10× the wall-clock median of the pinned release before this brief.

## Pre-mortem and detection

- A squash-merged witness still refuses because some ancestry check survived on the v2 path, because v2 was routed through `witnessTreeApplies` or `depFingerprintSame`, or because the dispatch sat after `classifyRevisionDetail` so v1's Expect read at the witness's base still ran. Caught by row 1 and its routing mutants in row 14.
- The dispatch sits after v1's Command check or state switch, so a changed Command, a recorded failure or a could-not-run on a v2 cell reports v1's reason with no gap name and `--coverage --json` has no `gap` for it. Caught by row 18 and its mutants in row 14.
- With the dispatch ahead of v1's Command check, nothing binds the citing Evidence Command cell, so a record whose `command_sha256` matches the current Verify row releases a row whose Evidence names a different command, and coverage releases what `checkWitnesses` and the witness gate refuse. Caught by row 18's inconsistent-record fixture (`witness-command-cell-mismatch`) and its mutant in row 14.
- A malformed `informational.commit` reaches `Claim.Revision` and `--coverage --json`. Caught by row 1 and its mutant in row 14.
- A symlinked input's target changes outside the required set and the link's unchanged blob id releases a stale pass. Caught by row 22 (`witness-input-symlink`).
- A `Repo` port error, a shallow boundary or a replace ref is read as a match or as a parent shape. Caught by row 19's shallow and replace-ref fixtures and row 14's mutants.
- A changed input releases (scope too narrow, digest computed at the wrong revision). Caught by row 2 and by the mutants in row 14.
- A recorded input leaves the required set (a file deleted under a declared directory, a removed `go.sum` or `go.work`) and is never compared, or an `absent` entry is treated as a matching digest. Caught by row 22 and by row 14's subset-test and `absent` mutants.
- A missing or tampered record releases, or `pending` is treated as bound. Caught by row 3.
- A future schema is read as v1 or v2. Caught by row 4.
- An older reader releases a v2 witness during a version skew. Caught by row 5, against a real prior release binary.
- The change loosens v1 by accident while sharing code. Caught by row 6's frozen-corpus comparison, whose non-vacuity check stops it passing on a corpus where both binaries refuse everything.
- A dependency or tool bump passes a stale witness. Caught by row 7.
- A network-dependent row is released by digest. Caught by row 8, within the selected policy. An unmarked host row whose network use the library cannot see remains possible under option 1; that is the stated residual risk, and option 2 closes it.
- CRLF or Windows paths change the digest, so witnesses refuse on another platform. Caught by row 9.
- A second parser or digest site appears outside the library. Caught by row 10's allow-list and plant.
- The board slows down with per-row git calls. Caught by rows 11 and 12; row 12's base is a fixed release tag, so it still compares two binaries after merge.
- A v2 cell hides the executing identity, so an implementer-run row counts as independent. Caught by row 16 and its per-read mutants.
- A valid record is replayed onto another row, brief or outcome. Caught by row 17.
- An Expect is loosened after a pass and v2 releases it. Caught by row 18.
- `cr` is a label nobody checked, a feature-branch commit with a merge-style subject passes as a landing, or a commit's subject matches a landing form its parent count contradicts. Caught by row 19. A rebase-landed single-parent commit whose subject mimics a squash suffix, or a GitLab fast-forward landing of a branch's own merge commit carrying another merge request's trailer, is not caught offline; the residual is a misattributed change request on a commit that did land, and only `--forge` closes it.
- A dirty edit outside the declared inputs hides behind matching digests. Caught by row 20.
- A reader of cells or records is missed and keeps its own interpretation. Caught by row 13's census.
- An author under-declares `inputs:` and a stale pass is released on a file the row read but did not declare. Caught only when the command names the omitted path literally (row 21). A transitively read file is not caught by any row here: human review of the declaration is the only control, and the observed-read check is the follow-up that would catch it (see single-point-of-failure).
- A record is forged by someone who can write Evidence. Out of scope by the trust assumption: v2 detects staleness, not forgery; authorship and review of the Evidence change request are the controls, as for v1.
- Rows whose subject is `docs/streams/**` content are judged with bookkeeping excluded, as today. Carried-over limit; review only.
