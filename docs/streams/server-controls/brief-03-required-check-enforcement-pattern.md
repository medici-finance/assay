# Brief 03 — The required-check enforcement pattern

## Context

files:
- `docs/streams/server-controls/required-check-pattern.md` (planned) — the reusable pattern + the
  three trust conditions + the self-attestation caveat.
- `docs/streams/server-controls/README.md` — brief-table row (generated by statusgen regen).
- `changelog/server-controls-03-required-check-pattern.md` (new) — highlight fragment.

single-point-of-failure: the ONE control a fine-grained rule depends on under this pattern is the
required status check itself. The pattern's whole job is to ensure that single control is NOT
also controllable by the party it polices — so the design deliberately builds the check's trust
from three INDEPENDENT properties (who reports it, where it runs, whether its source is
protected), each failing for a different reason in a different place. A check that satisfies only
one or two of the three is the single-point-of-failure this brief exists to forbid; there is no
"second convention" behind it, because a second convention shares the first's failure mode (see
the DR). The layers are the three conditions, not a duplicated assertion.

facts:
- The forge enforces "check X is green"; check X is operator code enforcing the fine rule. This
  is the only mechanism for a rule finer than the ruleset menu.
- `medici-finance/assay` runs a live instance: the `leak-sweep` ruleset (id 20872509) names a
  required status check `leak-sweep`, reported by a base-repo (house-side) runner the PR author
  does not control — the pattern in production.
- The three trust conditions, each independent: (a) **non-author identity** — the author cannot
  post the check's status; (b) **base-repo execution** — the check runs from the base repository,
  never the PR branch's own `pull_request` workflow (whose code the head author controls); (c)
  **protected source** — the check's own workflow/action/ruleset entry lives on a protected path.
- Violating any one degrades the check to **self-attestation**. A check missing (b) is the most
  common trap: `pull_request`-triggered jobs execute head code, so the author edits the check.

## Human decision
A pattern is being set for how every server-side rule finer than the forge's fixed protection menu
is enforced: as a required status check the merge gate demands, produced by our own code. The
decision is whether the three conditions that make such a check trustworthy are the right ones and
are stated strongly enough, because a check that misses any of them looks enforced while enforcing
nothing — the party the rule polices can quietly make it pass.

The three conditions proposed: the check reports under an identity the policed party does not hold;
the check runs from the base repository, never from the pull request branch's own build (whose code
that party controls); and the check's own source sits behind the same protection. A check that
meets only some of these is to be treated as advisory, never relied on as a real control.

Options:
1. **Approve the pattern and its three conditions as the fleet standard** — every future
   fine-grained control is built to this shape and reviewed against it; the cross-operator check is
   the first application.
2. **Approve with changes** — state which condition to strengthen, relax, or add; the pattern is
   re-authored before anything is built to it.
3. **Reject** — the pattern is parked and no fine-grained required check is standardised until a
   different design is agreed.

Default if no answer: none — the pattern blocks until answered, since briefs that build on it
cannot safely start without it.
