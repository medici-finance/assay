# Brief 05 — Reference cross-operator / independent-approver check

## Context

files:
- `docs/streams/server-controls/cross-operator-check.md` (planned) — the reference check design.
- `docs/streams/server-controls/README.md` — brief-table row (generated by statusgen regen).
- `changelog/server-controls-05-cross-operator-check.md` (new) — highlight fragment.

single-point-of-failure: the ONE control this design places between the collusion fault and a
merge is the required status check itself. Its trust is NOT single: it is the three independent
conditions of brief 03 (non-author reporting identity, base-repo execution, protected source),
each failing for a different reason in a different place — plus, behind it, the platform's existing
`require_last_push_approval` (which already stops the simplest case, author self-approves). So the
design is two layers that trip on different signals: the platform's last-push rule (a pushed head
cannot be its own approval) and the required check (a second, independent/non-colluding approver).
NONE is not the answer here — a second layer is feasible and this is it.

facts:
- Live state (freshness fact): `require_last_push_approval: true` and
  `require_extra_approval_for_unattributed_changes: true` on protect-main, so the head-pusher
  cannot supply the single approval. The base collusion case (one App pushes AND approves) is
  already blocked server-side.
- The **residual** the menu cannot express: (a) an **independent/second approver** requirement,
  and (b) **cross-operator collusion** — App A pushes, App B (a different role App) approves; the
  forge sees two legitimate Apps and is satisfied.
- The **reference check**: a base-repo workflow triggered on `pull_request_review`, reporting a
  `success`/`failure` commit status under a base-repo identity neither role App holds, that
  evaluates the approver rule at the PR head SHA — the approving login must be distinct from every
  identity in the PR's push/commit history (and, per the operator's chosen rule, drawn from an
  independent-approver set). Any other case (approver in the head's authorship set, stale
  `commit_id`, bot-only approval) posts `failure` or nothing (absent ≠ pass).
- The check is built to brief 03's three conditions and inherits its **negative-path obligation**:
  its own Verify table must simulate a colluding pair on a throwaway fixture and prove the gate
  reddens — never run against real protected main.

## Human decision
A server-side check is being designed to close a specific gap on this repository's protected main:
today the platform stops the person who pushed a change from being the one approval that lets it
merge, but it does NOT stop two different automated identities — one pushing, a different one
approving — from satisfying the gate together, because the forge cannot tell whether one operator
drives both. The decision is whether the proposed check closes that gap correctly: it would run
under a base-repository identity that neither of those automated identities holds, and require that
the approving identity be distinct from everyone in the change's own authorship, refusing the merge
otherwise.

What needs a human: is that the right rule (distinct-from-authors, plus an independent-approver
set if the operator wants one), and are the check's trust properties — who reports it, where it
runs, that a colluding pair is proven to redden it on a test repository — sufficient to rely on it?

Options:
1. **Approve the reference design as the closure for the #997 residual** — a follow-on authors the
   base-repo workflow and a human adds its context to the ruleset; the negative-path fixture proof
   is a merge condition on that follow-on.
2. **Approve with changes** — state the change to the approver rule or the trust properties; the
   reference design is re-authored before any workflow is built.
3. **Reject / accept the residual** — record that author≠approver is deemed sufficient and the
   finer residual is accepted; the check is not built.

Default if no answer: none — blocks until answered; the residual stays open and tracked meanwhile.
