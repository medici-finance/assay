# Brief 05 — Reference cross-operator / independent-approver check

## Context

files:
- `docs/streams/server-controls/cross-operator-check.md` (planned) — the reference check design.
- `docs/streams/server-controls/README.md` — brief-table row (generated by statusgen regen).
- `changelog/server-controls-05-cross-operator-check.md` (new) — highlight fragment.

single-point-of-failure: the ONE control this design places between the collusion fault and a
merge is the required status check itself. For the **author-self-approve** case that check sits
behind a genuinely independent layer: the platform's own `require_last_push_approval` trips on a
platform-tracked push event, a different signal than the check's posted review state. For the
**cross-operator** case — the residual this brief actually exists to close — the two layers are
NOT independent as originally framed: a colluding pair of distinct role Apps already satisfies
`require_last_push_approval` (they are different logins), and a check whose only rule is
"approver login differs from pusher login" is satisfied by exactly the same pair for exactly the
same reason. Two labels on one signal is not two layers. Genuine independence for the
cross-operator case requires the check's approver rule to read a SECOND, non-forge-visible signal
that login-distinctness cannot see: brief 03's condition (d), a **custodied independent-approver
set** the policed party cannot edit. That is why the design below makes that set MANDATORY rather
than an optional extra — without it, this brief's "two layers" claim does not hold for the case it
is written to close.

facts:
- Live state (freshness fact): `require_last_push_approval: true` and
  `require_extra_approval_for_unattributed_changes: true` on protect-main, so the head-pusher
  cannot supply the single approval. The base collusion case (one App pushes AND approves) is
  already blocked server-side.
- The **residual** the menu cannot express: (a) an **independent/second approver** requirement,
  and (b) **cross-operator collusion** — App A pushes, App B (a different role App) approves; the
  forge sees two legitimate Apps and is satisfied. Neither half is closed by evaluating the
  approver rule over login identity alone: two colluding Apps are, by construction, distinct
  logins, so a rule that only checks login-distinctness returns `success` on exactly the
  collusion it is meant to catch.
- The **reference check**: a base-repo workflow triggered on `pull_request_review`, reporting a
  `success`/`failure` commit status under a base-repo identity neither role App holds, that
  evaluates the approver rule at the PR head SHA. The rule has two MANDATORY parts, not one:
  (i) the approving identity is drawn from a **custodied independent-approver set** (brief 03
  condition (d)) — a roster held under the same non-author-controllable custody as the check's
  runner, with its location and its owner named, so the policed party cannot add a second
  identity of its own to the set; and (ii) the approving identity is distinct from every
  **platform-attested** actor in the PR's history — the push event actor and the review
  submitter as the platform records them, never the self-declared commit `author`/`committer`
  string alone, which the pushing party can shape freely. Condition (i) is what actually closes
  the cross-operator case; condition (ii) is the belt-and-suspenders check against a same-identity
  resubmission. Any other case (approver not in the custodied set, stale `commit_id`, bot-only
  approval, an identity attested only by a self-declared field) posts `failure` or nothing
  (absent ≠ pass).
- The check is built to brief 03's four conditions and inherits its **negative-path obligation**:
  its own Verify table must simulate a colluding pair on a throwaway fixture and prove the gate
  reddens — never run against real protected main. Condition (c)'s self-protection circularity
  applies directly here: a colluding pair able to merge into this repo is able to merge a change
  to the check's own workflow, or to the independent-approver-set file, unless that path carries
  its own mitigation (CODEOWNERS, a separate ruleset, or an out-of-repo definition) — the
  reference design must name one, not leave (c) reading as independent when for this application
  it is not by default.

## Human decision
A server-side check is being designed to close a specific gap on this repository's protected main:
today the platform stops the person who pushed a change from being the one approval that lets it
merge, but it does NOT stop two different automated identities — one pushing, a different one
approving — from satisfying the gate together, because the forge cannot tell whether one operator
drives both. Login-distinctness alone does not close that gap either: two colluding Apps are
already distinct logins, so a rule that stops there returns `success` on the exact case it exists
to catch. The decision is whether the proposed check closes the gap correctly: it would run under
a base-repository identity that neither of those automated identities holds, and require that the
approving identity be BOTH (a) drawn from a custodied independent-approver set the policed party
cannot edit, and (b) distinct from the platform-attested actors in the change's own history,
refusing the merge otherwise.

What needs a human: is that the right rule (approver drawn from a mandatory custodied
independent-approver set AND distinct from the platform-attested push/commit actors, not
login-distinctness alone); is the independent-approver set's custody (where it lives, who may
change it) specified concretely enough to rely on; and are the check's other trust properties —
who reports it, where it runs, that a colluding pair is proven to redden it on a test repository,
and that the check's own source and the approver-set file are protected from the same colluding
pair that could otherwise edit either — sufficient to rely on it?

Options:
1. **Approve the reference design as the closure for the #997 residual** — a follow-on authors the
   base-repo workflow and the custodied approver-set file, and a human adds the check's context to
   the ruleset; the negative-path fixture proof is a merge condition on that follow-on.
2. **Approve with changes** — state the change to the approver rule, the approver-set custody, or
   the trust properties; the reference design is re-authored before any workflow is built.
3. **Reject / accept the residual** — record that author≠approver is deemed sufficient and the
   finer residual is accepted; the check is not built.

Default if no answer: none — blocks until answered; the residual stays open and tracked meanwhile.
