# Brief 01 — Uniform-ruleset audit

## Context

files:
- `docs/streams/server-controls/ruleset-audit.md` (planned) — the target-menu definition + the
  per-repo current-vs-target table this brief produces.
- `docs/streams/server-controls/README.md` — brief-table row (generated by statusgen regen).
- `changelog/server-controls-01-ruleset-audit.md` (new) — the highlight fragment for the
  implementation PR.

facts:
- The **target menu** is the coarse, forge-fixed set the audit scores against:
  required-approval-count, require-last-push-approval, dismiss-stale-on-push,
  restrict-who-can-push, restrict-who-can-dismiss, required signed commits, block-force-push
  (`non_fast_forward`), block-deletion (`deletion`), required status checks. (GitLab equivalents:
  the same, plus *prevent approval by author* and *prevent approval by committers*.)
- The concrete repo set is NOT hardcoded in the deliverable: it is read at run time from the
  operator's configured repo set (the same repo set the desk reads). The audit template uses
  generic placeholders (`example-app`, `example-service`, `example-console`) so the shipped doc
  names no repo the reader cannot resolve; the run fills real repos from config.
- Reading is this brief; **applying** any changed setting is a repo-admin act performed by a
  human. This brief ends in a provisioning ask (the list of settings that differ from target),
  not a change.
- The rulesets read is `GET repos/{owner}/{repo}/rulesets` + the per-ruleset detail endpoint.
  A repo on classic protection returns no ruleset naming those settings — that is a real state
  the table records (and the exact case #1020 is about), not a read failure to paper over.

## Ground rules
- NEVER git push / trigger workflows / run mutating kubectl. Leave commits per the task only.
- **Read-only against every live repo** — this brief issues GET calls only; it changes no
  ruleset anywhere. A setting that differs from target is RECORDED as a provisioning ask, never
  applied.
- Stop at `implemented` — you do not set verified/done.
- If anything is unclear or contradicts repo state: report NEEDS_CONTEXT, don't guess.

## Task
1. Write `docs/streams/server-controls/ruleset-audit.md` (planned) with a **target-menu definition**
   section: one row per menu item above, each with its rulesets API field name and the target
   value (or "operator-set, record actual").
2. Add a **current-vs-target table**: one row per repo in the operator's configured set (real
   repos filled at run time; the shipped template uses `example-*` placeholders), one column per
   menu item, each cell either the live value read from the rulesets API or `classic — not
   readable via rulesets (#1020)` where the repo is on classic protection, or `could-not-read
   (no access)` where the executor lacks read access. No cell asserts a value without a backing
   read.
3. Add a **provisioning ask** section: the concrete list of (repo, menu-item, current → target)
   deltas a human/admin must apply to make the menu uniform. This is the brief's terminal output.
4. Record `medici-finance/assay`'s row from the live read (it is the one repo authoring can fully
   dereference): protect-main enforces the approver/last-push/dismiss/force-push/deletion items;
   its required-status-checks are carried by the separate `leak-sweep` ruleset.
5. Add a **recurrence trigger** section to `ruleset-audit.md`: uniformity is an operational
   commitment, not a one-time read (DR-server-controls `accepted` entry 1) — a repo added to the
   operator's configured set after this audit runs defaults to no ruleset, silently reintroducing
   the divergence the audit exists to catch. State the trigger explicitly and event-driven (a repo
   is added to the configured set), not calendar-driven, and name the owner: whoever maintains that
   configured set re-runs this brief's Task steps 1-4 against the added repo (or the whole set)
   before treating the menu as uniform again. This is a re-read of the same brief, never a new one,
   and a stale frozen table is not evidence the menu is still uniform.

## Pre-mortem → detection map

| Failure mode of the work | Caught by |
|---|---|
| A repo row's cell is typed from memory, not read | row 3 — the dereference re-reads live and fails on a value with no backing read |
| The audit hardcodes real repo names into the shipped doc (leak surface / staleness) | Review — the shipped template must carry `example-*` placeholders; the real set is run-time config |
| The doc lists gaps but no actionable deltas, so nobody knows what to change | row 4 — a current→target provisioning ask must be present |
| `medici-finance/assay`'s row drifts from live state over time | row 1 — re-run the live read rather than trust the frozen numbers |
| Uniformity is read once and assumed to hold forever; a repo added later silently reintroduces the divergence the audit exists to catch, with nothing that says who re-checks it | row 5 — the recurrence trigger and its owner must be stated in the shipped doc |
